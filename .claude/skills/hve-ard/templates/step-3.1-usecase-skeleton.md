# Step 3.1: ユースケース骨格抽出

## このステップの目的

事業要件文書を根拠に、**ソフトウェアが提供する価値**（自動化/可視化/最適化/判断支援/連携）が明確な
シナリオに限定してユースケースを抽出し、後続の per-UC 詳細生成（Step 3.2）で fan-out する対象となる
**ユースケース骨格** を `UC-*` ID 付きで列挙する。詳細記述は Step 3.2 に委譲し、本ステップでは骨格に留める。

## 入力

- `docs/business-requirement.md`（Step 2 出力。存在する場合はこちらを優先）
- `docs/company-business-requirement.md`（Step 1.2 出力。Step 2 がスキップされた経路でのフォールバック）
- `docs/recommended-kpi-okr.md`（Step 2.1 出力。**任意**。存在する場合のみ参照し、各 UC が満たす
  KPI/OKR ID を意識する。ファイルが無い場合はこの参照を行わない）

## 出力

- `docs/catalog/use-case-skeleton.md`

## 実行手順

1. 一次情報から、ソフトウェア提供シナリオとなる対象提言・論点を `REC-01`, `REC-02`... で抽出する。
2. 対象外（業務運用のみで成立する会議体・体制・教育・制度等）を明確に線引きし、混入させない。
3. 各提言から、**一次アクターのゴール達成単位（動詞＋目的語）** でユースケースを構造化する。
   画面名・単一処理名・単一 API 名で終わる粒度は禁止（過分割しない）。
4. 通常 10〜30 件、上限 50 件に絞り込む。
5. 優先度を付与する。
   - P0: 規制/リスク/収益・損失に直結、または致命的ボトルネック解消
   - P1: 運用効率・品質改善（代替手段はある）
   - P2: 将来拡張・高度化（MVP 後でも可）
6. 不明・推論項目は `TBD` と明示する。ブロッカー（アクター/トリガー/主要 I/O/境界が欠けて UC が
   成立しない場合）がある場合は最大 10 件までリストアップする。

## 出力フォーマット

`docs/catalog/use-case-skeleton.md` に以下の Markdown テーブルを含める。

```markdown
| UC-* | 名称 | 主アクター | 優先度 |
|---|---|---|---|
```

- `UC-*` の `*` は英数字・ハイフン・アンダースコアのみ（例: `UC-Signup`, `UC-01`, `UC-Member-Register`）。
- UC 数は通常 10〜30 件、上限 50 件。
- 詳細記述（前提条件・基本フロー・データ I/O 等）は Step 3.2 で行うため、本ステップでは骨格のみに留める。
- 抽出根拠となった `REC-*` との対応が分かる場合は併記してよい。

## 重要な注意事項

- Out of Scope の混入がないこと。粒度が揃っていること（画面/機能/処理の混在を抑制）。
- 重複がないこと（同義統合・包含関係の整理）。
- **捏造禁止**: ID・URL・固有名・数値・事実を根拠なく作らない。不明・未確認は `TBD` / `要確認` と明示する。
- **オーバーエンジニアリング禁止**: 指示・要件にない汎用化・抽象化・将来拡張の先回りを行わない。YAGNI に従う。
