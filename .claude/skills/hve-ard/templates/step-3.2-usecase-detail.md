# Step 3.2: ユースケース詳細（fan-out 子タスク）

## このステップの目的

Step 3.1 で抽出されたユースケース骨格のうち、**`{key}`（1 件の `UC-*`）のみ** について詳細仕様を生成する。
本テンプレートは fan-out の子タスクであり、1 ユースケース = 1 セッション（1 サブエージェント）で実行する。

## 入力

- `docs/catalog/use-case-skeleton.md`（Step 3.1 出力。`{key}` に対応する行）
- `docs/business-requirement.md`（Step 2 出力。存在する場合はこちらを優先）または
  `docs/company-business-requirement.md`（Step 1.2 出力。フォールバック）
- `docs/recommended-kpi-okr.md`（Step 2.1 出力。**任意**。存在する場合は当該 UC が満たす `KPI-*` /
  `OKR-*` ID を「KPI」項目に記載する。無ければ省略する）

## 出力

- `docs/usecase/{key}-detail.md`

ファイル名は必ず `{key}-detail.md` 形式とする（スラッグ等を付与しない。例: `UC-18-detail.md` であり
`UC-18-realtime-kpi-dashboard-monitoring.md` は不可）。`docs/catalog/` 配下やサブディレクトリには作成しない。

## 実行手順

1. `docs/catalog/use-case-skeleton.md` から `{key}` の行（名称・主アクター・優先度）を確認する。
2. `{key}` に限定して詳細仕様を作成する。他のユースケースへの言及は行わない。
3. 主要代替・例外は最大 3 件に絞り、それぞれ「条件→結果」の 1 行で記述する。
4. 主要データ I/O はデータオブジェクト名のみを記載する。
5. 不明・推論項目は `TBD` と明示し、理由・影響・埋め方が分かる形で残す。

## 出力フォーマット

`docs/usecase/{key}-detail.md` に以下の項目を含める。

1. ID / 名称 / 目的（価値）
2. 主アクター
3. 前提条件
4. 基本フロー要約（3〜5 行）
5. 主要例外（最大 3 件、各 1 行で「条件→結果」）
6. 主要データ I/O（データオブジェクト名のみ）
7. KPI（`docs/recommended-kpi-okr.md` が存在する場合のみ `KPI-*` / `OKR-*` ID を記載。無ければ省略）
8. 優先度（P0/P1/P2）

不明・推論項目は `TBD` / `要確認` と明示する。

## 重要な注意事項

- **対象は `{key}` の 1 件のみ**。他のユースケースの詳細記述・評価は行わない。
- **出力ファイルは `docs/usecase/{key}-detail.md` の 1 件のみ**。他の `UC-*` の出力ファイルを作成・更新しない。
- 既に `docs/` 配下に存在する他ユースケース・他ステップの成果物を変更しない。
- **捏造禁止**: ID・URL・固有名・数値・事実を根拠なく作らない。不明・未確認は `TBD` / `要確認` と明示する。
- **オーバーエンジニアリング禁止**: 指示・要件にない汎用化・抽象化・将来拡張の先回りを行わない。YAGNI に従う。
