# /implement — 構造化実装ワークフロー

ゲートベースの実装フローを実行するスキル。
規約の正本は `.claude/rules/hve/implement-flow.md`（HVE ルール）。

---

## 手順

正本（implement-flow.md）が定義する Step 0〜8 のゲートをそのまま実行する。

### Step 0: ブランチ作成

- main から作業ブランチを切る（`~/.claude/rules/git/branching.md` に従う）
- ブランチ上でなければコードを書かない

### Step 1: Plan（スコープ特定）

- ユーザーの指示の目的を理解する
- Issue がある場合は `gh issue view <N>` で本文を確認する
- Plan モードでタスクのスコープを把握する
- 影響する領域・モジュール・データモデルを列挙する
- Step 2 で検索すべきキーワード・領域を特定する

### Step 2: Knowledge 検索（Plan の各領域を網羅）

**Plan で特定した各領域について必ず実行する。**

1. **knowledge 検索**:
```sh
scripts/mdq search --q "<テーマに関連するキーワード>"
```

2. **コード検索**:
```sh
scripts/cq search --q "<関連する関数名・型名・概念>"
```

3. **シンボル追跡**（精密な定義・参照の追跡が必要な場合）:
   - `mcp__serena__find_symbol` で関連する型・関数を特定
   - `mcp__serena__find_referencing_symbols` で依存関係を把握

#### ゲート判定

| 結果 | 次のステップ |
|---|---|
| 既存実装と矛盾 | **STOP**: 矛盾するコード箇所を示して報告 |
| OK | → Step 3 |

### Step 3: 棄却済み案チェック

- Step 2 で見つけた決定ログの「却下した代替案」を確認する
- 特に D24（実験・棄却証跡）を確認する
- これから取ろうとするアプローチが棄却済み案と衝突しないか検証する

#### ゲート判定

| 結果 | 次のステップ |
|---|---|
| 棄却済み案と衝突 | **STOP**: 衝突する決定ログの ADR 番号・内容を引用して報告 |
| OK | → Step 4 |

### Step 4: ギャップ分析 → 質問票

Step 1〜3 の結果を踏まえ、実装に必要だが不足している情報を分類する。

- **ブロッキング**: 回答なしでは正しい実装方針を決められない
  - 例: 仕様の解釈が複数ある、既存コードの意図が不明、テーブル設計の選択肢がある
- **軽微**: 前提を明示すれば進められる
  - 例: エラーメッセージの文言、ログレベルの選択、変数名の好み

ブロッキングな不明点がある場合、構造化して提示し回答を待つ:

```
📋 質問票（回答をお願いします）

## Q1: <質問>
- 背景: <なぜこの情報が必要か>
- 推奨解: <推奨する回答>
- 理由: <推奨の根拠>

## Q2: ...
```

#### ゲート判定

| 結果 | 次のステップ |
|---|---|
| ブロッキングな不明点あり | 質問票提示 → 人間回答を待つ |
| 軽微な不明点のみ | 前提を `「前提: ...」` として明示し → Step 5 |
| ギャップなし | → Step 5 |

#### 回答後の分岐

| 回答の性質 | 次のステップ |
|---|---|
| アプローチを根本的に変える | → Step 1 に戻る（最大 2 周。超えたら STOP） |
| 新たな不明点が発生 | → Step 4 先頭に戻る（回答ごとに 1 回まで。連鎖する場合は STOP） |
| 解消 | → Step 5 |

### Step 5: テスト設計

**テストファースト**: 実装より先にテストを書く。

1. **受入基準の明確化**: 何が動けば「完了」かを箇条書きで列挙する
2. **テストケースの設計**:
   - 正常系（ゴールデンパス）
   - 異常系（エラーケース・境界値）
   - 既存機能への影響がないこと（回帰テスト）
3. **テスト実装**: 現時点では失敗するテストを書く（Red）

#### ゲート判定

| 結果 | 次のステップ |
|---|---|
| 受入基準が不明確 | → Step 4 に戻る（質問票で確認・最大 2 周。超えたら STOP） |
| OK | → Step 6 |

### Step 6: 実装

テストを通す実装を書く。

1. **実装**: テストが通る最小限のコードを書く（Green）
2. **リファクタ**: 必要に応じて整理する（Refactor）
3. **全テスト実行**: 回帰がないことを確認する
4. **動作検証**: 画面を伴う実装はブラウザテストを必須とする

impl-sonnet への委譲判断はモデル使い分け規約（`~/.claude/rules/workflow/model-selection.md`）に従う。

#### ゲート判定

| 結果 | 次のステップ |
|---|---|
| 同一テストが 3 回連続失敗 | **STOP**: アプローチの破綻を報告 |
| 影響範囲が想定超 | **STOP**: 報告（impl-sonnet 委譲中→メインループ引き取り） |
| テスト通過 | → Step 7 |

### Step 7: Knowledge 同期

実装で確定知の前提が変わった場合、knowledge を同じ PR で更新する。

1. **影響する knowledge の特定**:
```sh
scripts/mdq search --q "<変更した概念>"
```

2. **knowledge 更新**: 変更箇所のみ差分マージする（全書き換えしない）

3. **決定ログ追記**: 設計判断・ルール変更・棄却を伴う場合は決定ログに append する

4. **stale 検査**:
```sh
python3 scripts/bump-distilled-sha.py --all-stale --dry-run
```

5. **整合性検査**:
```sh
python3 scripts/check-doc-classes.py
python3 scripts/check-decision-log-immutability.py
```

#### ゲート判定

| 結果 | 次のステップ |
|---|---|
| knowledge 更新で矛盾 | **STOP**: `status: Conflict` を宣言、人間に報告 |
| OK | → Step 8 |

### Step 8: PR 作成

`create-pr` スキルを起動して PR を作成する。

```
Skill(skill: "create-pr")
```

create-pr スキルが以下を自動実行する:
- base 同期 + コンフリクト解消
- ブラウザテスト（該当時）
- リモートへプッシュ
- PR 本文作成
- セルフレビューループ（最大 5 巡）
- 最終報告

---

## STOP 時の報告テンプレート

```
🛑 実装フロー停止

■ 停止ゲート: Step N（ゲート名）
■ 理由: <具体的な停止理由>
■ 試みたこと: <探索・分析で得た情報>
■ 推奨アクション: <次にどうすべきか>
```

---

## 注意事項

- 各 Step の STOP 条件に該当したら、テンプレートに沿って停止する（黙って続行しない）
- Step 1 の Plan を省略しない。Plan なしに Knowledge 検索を始めると検索キーワードが足りず知識を舐めきれない
- Step 2 の Knowledge 検索を省略しない。「知っているから」は理由にならない（棄却済み案の見落としを防ぐ）
- Step 5 のテスト設計を省略しない。テストが書けない＝受入基準が不明確
- Step 7 の Knowledge 同期は「あとで」にしない。同じ PR で完結させる
