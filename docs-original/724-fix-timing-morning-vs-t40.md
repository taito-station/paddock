# #724 買い目を固める時点（朝 vs 発走 40 分前）— 計測ログ（2026-10-04〜05）

predict-watch は各レースが監視窓（40 分）に入った最初のスイープの選定を固定する（ADR 0078 / #601）。この固定を「朝の選定」に
前倒しすると回収率が変わるかを、10 開催日で測った記録。方針の確認は `qa/QA-fix-timing-724.md`、蒸留先は
`knowledge/ev-kelly-bet-selection.md`（決定ログ #724）。

## 1. 定義（実装の前に issue #724 で固定）

- **T-40**: 初回スイープの `captured_at` 以降で最初に保存された全券種のスナップショット（predict-watch はスイープの開始時刻を
  先に採番してからスクレイプ・保存するので、「以前で最も近い」だと odds-collect の古い単複を拾う）。時刻は `timestamptz` で比べる。
- **朝**: 当日 JST 0 時以降で最初に取った単勝のスナップショット（前日夜の fetch-card の薄いオッズを拾わない）。
  盤の「朝↔現」比較（#448・最初に全券種がそろった時点）とは別の定義。
- **出走馬**: その時点の単勝に載っている馬（出馬表は最終版しか残らず、後から分かった取消を朝の側が先に知ってしまうため）。
- **朝の固定の伝票**: 朝の盤で選んだ軸・相手・混戦を固定し、T-40 の盤（その時点の出走馬・オッズ）で `compose_portfolio` を組む。
  朝の後の取消は固定の規則（相手は落とすだけ・軸が取消ならライブの首位, REQ-D23-007）がそのまま効く。
- **統計**: 馬・騎手・調教師・コースの統計は開催日より前の結果だけ（`as_of`）。近走・標準タイムは従来どおり出馬表の日付で切る。
- **精算**: netkeiba の結果ページの払戻。取消・除外の馬を含む脚は返還（賭金にも払戻にも入れない）。配分は現行の 1500:1500:2000。
- **対象**: T-40 でスイープしていた 10 開催日（07-12・07-18・07-19・08-02・08-09・08-15・08-16・08-22・09-27・10-03）。
  朝と T-40 の差が 60 分未満のレースは外す。
- **判定**: 主判定は 09-27 を除く日（09-27 は仮説が生まれた日）。「朝 − T-40」のプール ROI の差について、レース単位ブートストラップ
  （2000 回・seed 571）の 95% CI が 0 を跨がず（正の側）、かつ差が 0 でない日の 7 割以上で朝が上のときだけ前倒しを提案する。

### 3.1 食い違いの原因の分類（計画の改訂 M5 の合否）

合否は「全件一致、または不一致を 1 件ずつ原因に分類して説明できる」こと。分類は (a) スナップショットの時点、
(b) 統計の取り込み時刻の差（as-of）、(c) コードの変更。

- **(a) 時点: 0 件**。T-40 のスナップショットの取得時刻 − 初回スイープの開始時刻は、227R で中央 75 秒・最大 205 秒で、
  スイープ間隔（300 秒）を超えたものは無い。odds-collect は単複しか保存しないので、拾ったのは全レースでその初回スイープ自身が
  保存した全券種のスナップショット。
- **(b)/(c) 入力の差: 25 件（軸 1・相手 24）すべて**。入れ替わった 2 頭の勝率の差（再構成の T-40 の blended）は 0.01〜0.52pt で、
  どれもその日の「記録の軸の勝率」のずれの最大値（0.52〜1.72pt）以内に収まる。記録の相手が再構成で 8〜10 番手（軸を含む順位）に落ちたレース
  （新潟 08-02 3R・札幌 08-15 12R・新潟 08-15 12R）も、6 番手以下が 0.4pt 以内に並ぶ近接で、同じ扱いになる。
  (b) と (c) は 1 件ずつには分けられない（当時のコードで再実行しないと切り分けられない）。
- 閾値は「その日のずれの最大」で、緩い側の基準。その日のずれの中央値と比べると、0.5pt 前後の数件は超える。
- **未分類: 0 件**。混戦の不一致は 0 件。
- **α の確認（(c) の一部）**: live の α はログに残っていない（`live_ev_snapshots` に α の列は無い）。既定値の定数
  `RECOMMENDED_MARKET_BLEND_ALPHA` は 06-30 から 0.2 のまま変わっていないが、起動時に `--blend-alpha` で上書きしたかは
  確かめられない。10-03 の一致（0.001pt）が、少なくともその日は α=0.2 で動いていた間接の証拠になる。
- 判定: 合格（全件を原因に分類して説明できた）。

### 3.2 母集合と時点の補足

- **出馬表の取得時刻（M3）**: `fetch_history` は 1 レースにつき最後の取得だけを残す。計測の対象 180R のうち 39R（主判定 167R の
  うち 38R）は、出馬表の最後の取得が朝より後だった。出走馬は単勝のスナップショットで決めるので母集合には効かないが、乗り替わり
  など朝の後に出馬表へ入った情報は、朝の側の再構成も知っている（朝の側に有利に働きうる）。
- **出走馬の取りこぼし**: 母集合は単勝のスナップショットに載っている馬にしている。読み出しで値域違反として捨てた単勝行の馬も
  外れるので、その馬の分だけ live（出馬表から母集合を取る）とずれうる。3.1 の照合では、これで説明が要る食い違いは出ていない。
- **記録◎の優先（Minor 6）**: 記録◎（pad）が初回スイープの選定より優先される規則は、対象の 10 開催日の `predictions` が
  0 件なので発火していない（2026-10-05 に DB で確認）。
- **朝の側の参考照合（09-27・M5）**: `docs-original/601-axis-lock-field-check.md` にある 09-27 11:15 の `--overview`（朝の blended
  選定）と、再構成の朝（11:04〜11:14 のスナップショット）を比べた。比較の意味がある 16R（阪神4R・中山4R は 11:15 のスイープで
  固定されたので外す）のうち 14R で軸・相手とも一致。残り 2R（阪神8R ⑧↔⑪・阪神9R ⑩↔④）は相手 1 頭の入れ替わり。
  時刻が最大 11 分ずれるのと、overview は read-through でオッズを取り直すため。601 の一覧で朝と固定が食い違った 4R
  （中山7R・阪神8R・阪神12R・中山12R）のうち 3R は、再構成の朝も overview と同じ選定だった。

## 5. 結論

- 朝に固定しても T-40 に固定しても、回収率に検出できる差は無い（差 +0.001、CI は 0 を大きく跨ぐ）。差が無いとは言えず、
  **この標本では MDE（対の差で約 ±0.30）未満の差は検出できない**。
- 選定は朝と T-40 でよく変わる（軸 16%・相手 45%）が、回収率の差としては表れていない。

## 6. 計測中に見つけた問題

- 結果ページの古いテンプレートで `nk.parse_result` が結果表の外の行を返し、後勝ちの辞書だと 1 着馬の着順が `None` に上書きされた
  （軸の勝率が 4% と出た）。計測スクリプトは `finish_ranks`（名前の無い行を捨て、最初の行を採る）で回避した。共有部品の修正は #766。
  判定の ROI は払戻の辞書で精算しているので影響していない（修正の前後で判定の数字は同じ）。

## 7. 再現

```sh
# 両時点の伝票（読み取りのみ）。出力は gitignore 済みの work/ に置く（DB 由来のデータを public リポに入れない）
mkdir -p work/724
PADDOCK_LOG=error paddock-analyze reconstruct-slips --date 2026-08-15 > work/724/2026-08-15.jsonl
# 精算と判定（払戻は結果ページのキャッシュから。ネットワークには出ない）
NK_RESULT_CACHE_DIR=<primary>/scripts/predict-check/.cache_nk_result_html \
  python3 scripts/predict-check/fix_timing_probe.py work/724/2026-*.jsonl
# 再構成の検査（§3）。記録の軸の勝率は初回スイープの live_ev_snapshots から取る
psql -At -F $'\t' -c "select race_id, axis, axis_prob from (select race_id, axis, axis_prob,
    row_number() over (partition by race_id order by captured_at::timestamptz) rn from live_ev_snapshots
    where date between '2026-07-12' and '2026-10-03') t where rn = 1" > work/724/axis_prob.tsv   # axis_prob は %
python3 scripts/predict-check/fix_timing_probe.py --check-recorded --axis-prob work/724/axis_prob.tsv work/724/2026-*.jsonl
```

- `reconstruct-slips` は 1 レースにつき朝と T-40 の 2 回、統計を引き直す（重い）。共有 DB に負荷がかかるので、
  監視（predict-watch / odds-collect）や backtest と並走させない。
