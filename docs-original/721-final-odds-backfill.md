## 2. 取得の方式（計画承認時の決定と、その後の変更）

- 保存はファイル（生の応答 JSON ＋ 解析用 TSV）。DB に表を作らない・`race_odds` を上書きしない（質問票 Q2）。
- 取得・パースは Rust（`paddock-fetch-final-odds`）。既存の `netkeiba-scraper`（オッズ API の URL 構成・`parse/odds.rs`）と
  ドメインの番兵判定（`OddsValue::try_from`）を再利用し、二重実装を作らない（ADR 0064）。
  - issue の要件 4 は Python の `odds_guard.is_payout_odds` での除外を指定していたが、同じ番兵リスト（`netkeiba_sentinels.txt`）を読む
    Rust 側の判定に置き換えた（取得・パースを Rust に置いたため）。
  - 計画では `paddock-analyze` のサブコマンドとしていたが、既存の取得系アプリ（fetch-card / fetch-history / fetch-results）と
    並べて独立したアプリにした（netkeiba-scraper への依存を analyze に持ち込まない）。
  - 対象レースは DB から読み取り専用の SQL で一覧ファイルにして入力する。`find_finished_races_between` は `source='pdf'` に
    限るため、DB 接続に依存しない形にした。
- **間隔**: 本取得は 3,000ms（リクエスト前の sleep）で走らせた。実測は 3.09 秒/件（約 0.324 rps）で、issue の要件「`--max-rps 0.3` 相当」（3.33 秒/件以上）を
  わずかに超えていた（PR のレビューで判明）。以後は下限を 3,334ms にした（CLI が未満を拒否）。並列化しない。
  - 取得失敗で即停止。本取得の時点では、共有のリトライ（transient 失敗で 1 秒・2 秒のバックオフ）を通っていた。レビュー後は**再送しない**
    （1 回の失敗で止めて、時間を空けて再開する）。確定でない応答が 3 回続いても停止（回数は定数で CLI から変えられない）。
  再開は保存済みファイルのスキップで行う。
  - 計画の初版は「本番 scraper の既定 1 秒」を根拠に 1.2 秒としていたが、開発ルール監査で差し戻した
    （「1〜2 秒で連打しない」はユーザーの明言。既定 1 秒は当日の少数リクエスト向けで、万件のバックフィルの根拠にならない）。
  - 全 5,509R × 3 リクエスト = 16,527 リクエスト。実測で約 14 時間。

## 3. 着順の補完（結果の無い出馬表レース 457R）

- 対象: 予想日に出馬表（`race_cards`）だけ取り込み、結果が無かったレース 457R（2026-06-20〜09-27 の 16 日）。
- 経路: `ResultsInteractor::refresh`（`POST /api/results/{date}:refresh?force=true`。`upsert_results` は INSERT でき、既存値は COALESCE で残す）。
  `paddock-fetch-results` は既存行の UPDATE 専用（ADR 0015）なので使わない。
- api-server の scraper は間隔 1 秒固定だったので、`PADDOCK_NETKEIBA_INTERVAL_MS` を足して取り込み用のサーバだけ 3.5 秒にした
  （未設定なら従来どおり）。レビュー後、既定の 1 秒より短い値は起動時に拒否するようにした。
- 手順: 共有 DB をコンテナ内 PG17 で隔離 DB `paddock_test721` に複製（1 分 45 秒）→ 隔離 DB で 16 日分を取り込み → 件数と中身を確認 →
  `scripts/backup-db.sh`（pinned に `pre721-results-20260929-172924.dump`）→ 共有 DB に同じ手順。
- 隔離 DB の結果:
  - races 5,052 → 5,509（+457）、結果の無い出馬表レースは 0。
  - 出馬表のあるレースの results: finished 9,270 行（着順・単勝オッズ・人気・タイム・騎手すべて埋まる。馬体重 9,267）、
    did_not_finish 34、scratched 36、cancelled 7。
  - 買い目の精算は 16 日とも 0 件（対象の買い目なし）。
- 既知の制約: refresh が作る `races` 行は `track_condition`・`weather` を書かない（同日取り込みの設計。結果ページから取らない）。
  この 457R は馬場状態が空になる（#720 の特徴量では良と同じ扱い）。`source` は既定の `pdf`（実レースの区分・設計どおり）。
- **この経路のペーシングの実態**: refresh は結果ページの取得に共有のリトライ（transient 失敗で 1 秒・2 秒の再送）を通り、取得に失敗しても
  warn を出して次のレースへ進む。間隔 3.5 秒の指定は「成功した取得どうしの間隔」で、再送の瞬間は下回り、拒否（403・429）が始まっても
  その日の残りを叩き続けうる。今回の 457R では warn は出なかった（全日とも取り込み件数が出馬表と一致）。
- 取り込んだ 457R の race_id 一覧を凍結した（§6 `imported-457-race-ids.txt`）。
- 作業中の失敗: zsh で `"$d:refresh"` と書くと `:r` が拡張子を外す修飾子として解釈され、URL が壊れて 404 になった（隔離 DB で気づき、`${d}` で再実行）。
- issue 要件 3 の「結果未取り込みの 441R」（`race_odds` はあるが着順の無いレース）はこの 457R に含まれる。取り込み後、
  `race_odds` のある 685R（ワイドは 593R）はすべて着順を持つ。
- 共有 DB の結果: 16 日とも隔離 DB と同じ件数（races 5,509・results 76,392・結果の無い出馬表レース 0）。
  results の主要列（race_id・馬番・着順・status・単勝オッズ・人気・タイム）を並べたハッシュが隔離 DB と一致。買い目の精算は 0 件。

## 4. 本取得（2026-09-29 18:01 〜 09-30 08:18・保存ファイルの時刻）

- 対象: 結果のある全レース 5,509R（`races.txt`・読み取り専用の SQL で作成）× 3 券種 = 16,527 リクエスト。間隔 3,000ms の指定で、実測 3.09 秒/件（最小 3 秒・約 0.324 rps。保存ファイルの時刻から算出）。
- 途中で 1 回停止: 12,337 件目の次（`2026-1-chukyo-5-1R` のワイド）で名前解決（DNS）の失敗。netkeiba の拒否（403・429・接続リセット）ではなく
  手元のネットワークの一時断。停止は設計どおり（取得失敗で即停止）。疎通を確かめて同じコマンドで再開し、残り 4,190 件を取得（取得済み 12,337 件はスキップ）。
- 結果: **16,527 件すべて status=`result`（確定）、確定でない応答 0、`official_datetime` の欠け 0**。
- TSV（`emit`）: 3,222,001 行。

| 券種 | 応答の組合せ | 出力行 | 番兵 | 値域違反 | 読み飛ばし |
|---|---|---|---|---|---|
| 馬連 | 515,456 | 511,694 | 0 | 3,762 | 0 |
| ワイド | 515,456 | 511,694 | 0 | 3,762 | 0 |
| 3連複 | 2,229,885 | 2,198,613 | 7,009（877R） | 24,263 | 0 |

- 値域違反の大半は取消・除外の馬を含む組合せ。netkeiba は負の値（`-3.0` または `-2.0`・人気 9999）で返す
  （馬連 `-3.0` 3,393・`-2.0` 369、ワイド `-3.0` 3,393・`-2.0` 369、3連複 `-3.0` 21,909・`-2.0` 2,353・`0.0` 1）。除外すると、馬連・ワイドの出力行数は
  **5,493 / 5,509R で C(出走頭数, 2) と一致**した。
- 3連複の番兵 `99999.9`（応答の表記は `99,999.9`）は、確定後も票の入らなかった組合せ（人気が最下位付近）。払戻倍率ではないので除外している（ADR 0086/0088 の規約どおり）。
  **#722 で 3連複の市場確率を作るときは「売れていない組合せ」として扱いを決める必要がある**。番兵を含めて数えると、3連複は 5,492 / 5,509R で C(出走頭数, 3) と一致。
- 一致しないレース:
  - 16R: DB の results に 1〜5 頭分しか行が無い（#730 で見つかった「行が足りない 16 本」）。オッズ側は全頭分ある。補完は #742。
  - 1R（`2026-2-hanshin-7-4R` の 3連複）: 1 組（4-12-15）だけ `0.0`・人気 9999 で返る netkeiba 側の特異値（的中の組ではない）。値域違反として除外。
- **揃うレース数（確定オッズ＋着順）: 馬連・ワイド・3連複とも 5,493R**（結果のある 5,509R から、行が足りない 16R を除く）。
  定義は「確定オッズの応答と、出走馬の着順行が揃うレース」。3連複の組合せが TSV に全部あるのは 5,492R（`2026-2-hanshin-7-4R` が 1 組欠ける）で、
  877R では番兵（無投票の組合せ）が TSV に無い。
