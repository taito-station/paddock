# 監視ループのスリープ耐性（predict-watch / odds-collect）

終日バックグラウンドで回る 2 つの監視 app は、ループ骨格 `src/interface/monitor-loop/` を共有する。
ホスト（macOS ラップトップ）のスリープを跨ぐことが常態なので、**時間軸は wall-clock を正とする**。

## 前提: 何が壊れうるか

監視の失敗は**沈黙として現れる**。通知が来ないことは「妙味が無かった」と区別がつかないため、
止まっていたこと自体に気づけないのが最大のリスク（2026-08-01 に約 12 レースが未評価のまま流れた）。
したがって設計要件は「止まらないこと」だけでなく **「止まったら必ず言うこと」**、
そして **「通ったら必ず届けること」**（#584）を含む。

## 4 つの規律

### 1. 待機は wall-clock 期限への刻み待ちにする

次スイープの期限を `Local::now() + interval` で決め、**5 秒刻み**で現在時刻と期限を比べ直す
（`driver::sleep_until_with_tick`）。単発の長い `tokio::time::sleep` はホストのスリープ中に満了せず、
復帰後も「残り」を待ち続けて監視が無言で止まる。刻み待ちなら OS がタイマーをどう扱ったかに関わらず
「今が期限を過ぎているか」だけで判断でき、**復帰時点で期限を過ぎていれば即座に次スイープが走る**。

**刻み幅 5 秒の根拠は 8/1 の実事象**。`tokio::time::sleep` は単調時計基準で、macOS ではスリープ中に
進まない＝ティックは「起きている時間」でしか消化されない。あの日の Standby は **7 秒の DarkWake が
4 回（累計 28 秒）** だったので、30 秒刻みでは 1 ティックも満了せず再スイープに到達しない。
5 秒なら DarkWake 1 回ごとに満了して期限超過を検知できる。空回りのコストは既定間隔で 60〜180 回/スイープ、
1 回あたり時刻比較のみなので無視できる。

それでも**「再開の速さは awake 時間で数える」**という性質は残る。蓋を開けた本格復帰なら 5 秒以内、
DarkWake だけの Standby なら DarkWake 1 回ぶん待つ。発走直前 EV の判断粒度（分オーダー）には響かない。

### 2. 途切れたら必ず警告する

**スイープ開始どうしの実間隔**が `想定間隔 × 2 ＋ 前スイープの所要時間` を超えていたら
`⚠ 前回スイープから N 分空きました…` を出す。ログにこの行があれば、その間に発走したレースは
評価されていない。**この警告が出ている日の「通知ゼロ」は妙味なしの根拠にならない**。

- 測る区間を「待機」ではなく「スイープ開始どうし」にしているのは、**スイープ実行中に寝られた場合を
  取りこぼさない**ため（待機だけを測ると、その後の待機は想定どおりに見えて沈黙する）。
- 閾値に**前サイクルの所要時間**を足すのは、サイクル自体が長い日（predict-watch は
  `scrape_delay` × 対象レース）に毎サイクル誤警告が出ると、警告そのものが無視されるようになるため。
- **所要は単調時計（`Instant`）で測る**。壁時計で測ると `実間隔 = 所要 + 待機` /
  `閾値 = 2×interval + 所要` で所要が相殺され、発火条件が `待機 > 2×interval` に退化する
  ＝**スイープ中に寝られたケースを検知できない**（測る区間を広げた意味が消える）。
  単調時計はスリープ中に進まないので、スリープぶんは実間隔にだけ現れる。
- **警告は継続時だけでなく終了時にも出す**。日付を跨いで復帰したケース（＝ 8/1 の実事象そのもの）は
  下の「日付で終了する」経路に入るので、そこで黙ると**丸一日未監視だった日が警告なしの正常終了に
  見える**。終了行の直前に空き時間と最終スイープ時刻を必ず出す。

### 3. 終了は wall-clock の日付で決める

発走状態判定 `classify` は `NaiveTime` 同士の比較で**日付を持たない**。当日運用では十分だが、
日付を跨ぐと翌朝の `now` が全 post_time より前に戻り、昨日のレースが再び「発走前」に見える。
`should_continue` は永久に true を返し、**構造的に終われない**（実測: 最終レース発走から 14 時間経過後も生存）。

そこで継続判定に `should_stop_by_date(対象日, 現在日)` を併用し、対象日を過ぎたら終了する。
現在日は**ホストのローカル日付**をそのまま使う（運用ホストは JST 固定。前提が崩れていれば
`warn_if_not_today_jst` が起動時に警告する。判定側に TZ 変換を持ち込むとコードとテストの基準が割れる）。
判定は**ループ先頭**に置く。理由は 2 つ:

- **前日レースを再スクレイプする 1 巡を作らない**。odds-collect は windowless（発走前なら常に Due）なので、
  翌朝に復帰した `now` では前日の全レースが再び Due になる。スイープ後に判定すると、終了直前に
  全レースぶんの再スクレイプが走り `race_odds` / `race_odds_snapshots` に翌日タイムスタンプの行が積まれる。
- **`load_slots` が失敗し続ける経路でも必ず終わる**。DB エラーは握って `continue` するため、
  判定がループ末尾にあるとこの経路だけ迂回され「終われない」状態が残る。

`--once`（明示的な単発実行・cron / 検証用）は日付では止めない。ただし過去日なら
「発走済みレースのオッズを再取得して保存する」旨を警告する（黙って時系列を汚さない）。

- 実務上の見え方: `--date` に過去日を渡すと（`--once` 以外は）**1 スイープも走らず終了する**。
  `── {監視|収集}終了: 対象日（YYYY-MM-DD）を過ぎました。…` が出る。誤用そのものは起動時の
  `warn_if_not_today_jst` が別途警告する。
- **この終了行が当日の最終レース発走より前に出ていたら異常**（途中で寝ていた）。その場合は
  直前に途切れ警告と最終スイープ時刻が並ぶので、そこで見分ける。

### 4. 通過は通知で届ける（predict-watch のみ・#584）

規律 1〜3 は「止まったら言う」だが、**動いていても届かなければ同じ**。predict-watch は判定を
stdout に出すだけだったため、2026-08-09 は 82 スイープを途切れ警告 0 件で完走しながら、判定行は
20,744 行のログの 0.93%（192 行）に埋もれたまま開催が終わった。ゲートを通過したレースは
**macOS 通知として発火させる**。

- **配送は既存 shell の `notify()` と同一機構**（osascript の `display notification`）。
  `scripts/predict-check/snapshot_coverage_check.sh` 等 4 本と同じく、本文は **argv 経由**で渡し
  （`"` や `\` で壊れない）、失敗は握って本処理を止めず、title は `paddock <機能>` 命名
  （predict-watch は `paddock watch`）。Rust から叩くのは配送機構の共有であって判断の二重実装ではない
  ——**実利は権限にある**。osascript への通知許可は #493 で既に付与済みで、別クレートを入れると
  別 bundle の許可が要り、未許可のまま無言で鳴らない＝潰したい沈黙を新しい形で作る。
- **発火閾値は `--notify-roi`。表示ゲート `--notify-gate`（🔍 マーク）とは別物**で、後者は
  ベルを鳴らさない。未指定なら `--roi-gate` と同値。**下げるときは `--notify-gate` も揃える**
  ——揃えないと表示は `・`（低シグナル）のままベルだけ鳴る。起動時に食い違いを警告する。
- **既定（`--roi-gate` = 100%）では構造的に鳴らない**——ADR 0076 の 182R / 839 スイープでも
  4 開催日 246 スイープの実測でも通過 0 件。閾値の較正は #571 の担当で、経路（#584）とは独立に解く。
  経路が無いまま閾値だけ較正すると、較正した瞬間の判定がまたログに埋もれる。
  **だからこそ起動時に発火閾値と表示ゲート 2 つを 1 行に並べて宣言する**（機能要件と同格。無いと
  「鳴らない＝妙味なし」と「そもそも既定では鳴らない」が区別できず、上の前提が名指しする
  静かな失敗をそのまま作る）。実地検証は `--notify-roi` を下げて行う。
- **注記自身が嘘をつかないようにする**。ADR 0076 の「通過 0 件」を引くのは**実際に測った
  閾値（≥100%）以上のとき**だけ。`--roi-gate` を 0.7 へ下げた探索運用でも同じ文言を出すと、
  測っていない閾値について「鳴りません」と宣言することになる——一次資料自身が 2026-08-09 に
  ≥70% の通過を 7 回観測している。沈黙を潰すための注記が嘘をつくと目的が反転する。
- **重複抑制は「レースごと初回 ＋ 前回通知時から +10pt 上振れ」**。同じレースは窓 40 分 /
  間隔 5 分で 8 回前後 Due に入る。2026-08-09 の新潟10R は 7 スイープ連続で通過帯に入り
  ROI は 73.9 → 80.3 → … → 76.1（振れ幅 6.4pt）だったので、このルールなら 7 通知が 1 通知に落ちる。
  記録するのは**通知した**ときの ROI だけ（見送った pass で状態を汚すと、次に本当に通過したとき鳴らない）。
  状態はプロセス内メモリのみで**永続化しない**——再起動後に必要な初回通知を落とす側に倒れるため。
- **一次情報はログの `🔔` 行**。`🔔` は osascript の成否に関わらず出し、**配送できなかったものは
  `🔔(未配送)`** と印を付ける。したがって**数えるときは印を除く**——`grep '🔔 '`（末尾スペース）か
  `grep '🔔' | grep -v 未配送` で、数えられるのは「実際に配送できた件数」（抑制で見送ったものは行に出ない）。
- **`🔔` は「バナーが出た」ことまでは保証しない**。osascript は通知許可が無い・集中モード・
  バナー抑止でも exit 0 を返すので、保証できるのは「osascript の起動と実行に成功した」までで、
  そこから先は表示セッション依存のベストエフォート（`nohup` 起動のログインセッション内なら出るが、
  SSH / daemon 領域からは出ない）。**この差は実地で確かめるまで埋まらない**（次の開催日に確認する）。
- 配送失敗の警告は連続する間は再掲しないが、**一度成功したら再アームする**——プロセス生存期間の
  one-shot にすると、画面ロック等の一過性の失敗 1 回でその日いっぱい沈黙する。
- **配送はデッドライン付きでブロッキングプールへ逃がす**。同期の `Command::status()` を async の
  スイープから直に呼ぶと、osascript が返らないとき**監視ループごと止まる**。しかもプロセスは
  生存するので規律 2 の途切れ警告も出ない（警告は次のスイープが始まって初めて測れる）——
  通知の実装が沈黙を作っては本末転倒なので、5 秒で打ち切って失敗扱いのまま先へ進む。
- **osascript は絶対パス（`/usr/bin/osascript`）で叩く**。PATH 汚染で別バイナリを踏まず、
  将来 launchd 化しても最小 PATH で解決できる。
- **通知が鳴っても go シグナルではない**（ADR 0079）。発火は参考ROI 由来なので、🔶 / 🔍 と同じ制約下にある。

## スリープ抑止は骨格の責務ではない（#264 に一本化）

監視バイナリは**スリープ抑止を持たない**。抑止は launchd エージェント
`com.paddock.keep-awake`（#264・`caffeinate -i`）に一本化する。

理由: `caffeinate -i` が止められるのはアイドルスリープだけで、

- **蓋を閉じれば寝る**（clamshell sleep）。2026-08-01 の事象はまさにこれが起点で、
  **監視プロセスが自前で抑止を持っていても防げなかった**。
- `pmset` のスケジュールスリープ・強制スリープ（`pmset sleepnow`）も止められない。
- 既に寝ているホストを起こすこともできない。

つまり耐性の本体は上の規律 1〜3（寝ても壊れないループ）であり、抑止は best-effort。
#264 が既に同じことをしている以上、骨格に第二実装を置く価値は無い（ADR 0064 が戒める second source）。

**運用上の帰結**:

- 開催日は `deployments/launchd/install.sh`（keiba-start Step 1.6）で keep-awake を有効にする。
  **install を忘れると抑止はゼロ**——ただし監視自体はスリープを跨いでも復帰し、空いた分を警告する。
- **外出中に監視を当てにするなら、蓋を閉じない**（または常時稼働ホストへ移設する。
  [deployments/launchd/README.md](../../deployments/launchd/README.md) の既知課題）。
- **抑止窓は毎サイクル追従する（#585）**。窓は「当日の最終 `post_time` + buffer」で `caffeinate -t` に
  焼き込まれるので、**朝の install 時点で `fetch-card` が途中までしか終わっていないと短いまま固定される**
  ——2026-08-08 は 3 鞍ぶんの post_time しか無く 10:40 までの窓で張られ、10:26 に全 33 鞍（最終 18:30）が
  入っても伸びず、`StartInterval`(5 分) ぶんの抑止空白が空いた。現在は毎サイクル DB を引き直して
  必要窓が現行より後なら張り直す（**新しい `caffeinate` を起動してから旧を落とす**ので空白は生まれない）。
  それでも `install.sh` は `fetch-card` の後に叩くほうが良い（初回から正しい窓になる）。
  **実 launchd で確認済み**（2026-08-20）——`AbandonProcessGroup` 下で caffeinate がジョブ終了後も存続し、
  tick を跨いで lock が読まれ、張り直しの前後で `pmset` の抑止が途切れない（633 サンプル中 0 件）。
- **抑止窓の記録は分粒度**（#585）。lock に書く終了時刻はエポックを分境界へ丸めた値で、
  秒針を混ぜると「必要窓は変わっていないのに毎回延長する」という判定の揺れを生む。
- **lock は UID スコープの固定パス**（keep-awake は `/tmp/paddock-keep-awake-$(id -u).lock.d`・#643、
  prefetch は `/tmp/paddock-prefetch-$(id -u).lock{,.d}`・#651）。`$TMPDIR` は
  使えない——launchd は `TMPDIR` を設定せず `/tmp` に落ちるため、端末（`/var/folders/.../T/`）と別の
  lock を見て互いを見失う（2026-08-19 実測）。**keep-awake のパスは `keep_awake.sh`（作成側）と
  `uninstall.sh`（削除側）の両方が持つので、変えるときは必ず同時に直す**（prefetch は
  `prefetch_odds.sh` 1 本だけが持つ。`uninstall.sh` は prefetch の lock に触らない）。
  uid を挟むのは同一ホストの別ユーザーとの**事故**衝突を避けるためで、**悪意ある先回りは防げない**
  （`/tmp` の sticky bit が禁じるのは他人のエントリの削除だけで、新しい名前の作成は誰でもできる）。
  防げないので **「沈黙しない」に倒す**——lock が symlink / 他ユーザー所有なら大きく警告して
  **非 0 で終える**（`exit 0` のスキップに倒すと、時効による自己回復も `rmdir` 失敗で効かないまま
  外形正常に見え、次の開催まで気づけない）。
- **旧パスからの移行は「譲るか片付けるか」を実行中判定で分ける**（#643 / #651）。旧 lock を掴んだまま
  走っているインスタンスを取りこぼすと、新旧が互いを見失って**二重起動**する（prefetch では
  netkeiba への取得回数が倍になり ADR 0068 の IP ブロックに直結する）。実行中かどうかの材料は
  **lock が何を記録しているかで変わる**: keep-awake は pid を書くので生存＋`comm` 照合で判定し、
  **prefetch は何も書かない短命ロック**（`mkdir` ＋ `trap rmdir`）なので **mtime の時効（30 分）だけ**で
  判定する。prefetch の lock に pid を持ち込む案は、長命ロックでないのに「pid 未記入の窓」
  「PID 再利用」の分岐を輸入することになるため採らない。
  **prefetch は実機の既定パスで確認済み**（2026-08-22）——時効切れの旧 lock は回収されて
  `prefetch 開始:` まで到達し、`/tmp/paddock-prefetch-$(id -u).lock.d` を塞ぐとスキップし、
  終了後に lock は残らない。
- **`flock` の有無で lock 機構が変わる**（prefetch）。素の macOS に `flock`(1) は無いので**本番は
  `mkdir` 経路**、ubuntu の CI は `flock` 経路に入る。つまり **CI が緑でも本番経路が検査されたとは
  限らない**——回帰テストは PATH を絞って `flock` を隠し、両経路を踏ませる。

## 検証のしかた

実スリープを跨ぐ挙動は、DB / netkeiba 非依存の手動テストで確認できる:

```sh
cargo test -p monitor-loop -- --ignored --nocapture crosses_real_host_sleep
# 起動後に別端末で `pmset sleepnow`。
# 復帰させて「⚠ 前回スイープから N 分空きました」＋直後のスイープが出れば OK。5 スイープで自動終了。
```

本番と同じ `run_monitor_loop` を 1 分間隔で回すので、骨格の変更はこのテストで実機検証できる。
自動テスト（`cargo test -p monitor-loop`）側には、期限超過時の即時復帰・刻み跨ぎの待機・
途切れ判定の境界・日付跨ぎ終了が入っている。

通知（規律 4）は `cargo test -p predict-watch` に純関数テストが入っている——閾値解決・発火判定・
本文の 4 項目・起動注記の文言に加え、**2026-08-09 新潟10R の実測 ROI 列（73.9 → … → 76.1）を
そのまま流して 7 通知が 1 通知に落ちることを固定**している。実際に osascript が叩けるかは
macOS の表示セッションが要るので手動テスト:

```sh
cargo test -p predict-watch -- --ignored --nocapture sends_real_notification
# 本文に " と \ を混ぜてあり、argv 渡し（AppleScript 文字列補間をしない）の検査を兼ねる。
```

開催日の実地確認は `--once` に `--notify-roi` を下げて渡し、`🔔` 行と通知バナーの文言が
一致することを見る。

### ADR 0072: 監視ループを wall-clock 基準にし、ホストのスリープに耐えさせる (2026-08-04) — 承認済み

#### ステータス

承認済み（本 PR で実装）。対象 Issue: [#568](https://github.com/taito-station/paddock/issues/568)。

#### コンテキスト

`paddock-predict-watch`（発走直前 EV 監視）と `paddock-odds-collect`（単複オッズ時系列収集）は、
ADR 0060 の「軸ロック＋ズレ増額」を実行するための
decision-support であり、**終日バックグラウンドで回り続けること**が前提の運用（keiba-start Step 5）。
両者はループ骨格 `monitor-loop`（#459 で共通化）を共有する。

2026-08-01、この前提が壊れた。監視は 14:32 のスイープを最後に沈黙し、
**14:50〜18:30 発走の約 12 レースが一度も評価されないまま**、翌朝までプロセスが生存し続けた
（生ログ: [docs/original-docs/568-monitor-sleep-gap.md](../original-docs/568-monitor-sleep-gap.md)）。

コードを読むと、独立した 2 つの欠陥があった。

1. **単発の長い sleep がホストのスリープを跨げない**。骨格は 1 スイープごとに
   `tokio::time::sleep(interval*60)` を 1 回呼ぶだけで、現実の経過時間（wall-clock）と突き合わせない。
   ホストが Standby / DarkWake を繰り返す間このタイマーが満了せず、次スイープに到達しなかった。
   復帰しても catch-up せず、**途切れた事実がログにも残らない**。
2. **終了判定が「時刻」しか見ていない**。発走状態判定 `classify(now: NaiveTime, post_time: NaiveTime, …)`
   は日付を持たない。日付を跨ぐと翌朝の `now` が全 post_time より前に戻り、昨日のレースが
   再び「発走前」と判定される。`should_continue` は永久に true を返し、**構造的に終われない**。

沈黙は運用上「妙味が無かった」と読まれる。**静かな失敗**であることが本件の最大の危険性で、
「途切れたら気づけること」も要件に含める。

なお macOS のスリープ抑止は既に `com.paddock.keep-awake`（#264・launchd ＋ `caffeinate -i`）が存在するが、
これは締切前 prefetch（#237）の launchd タイマーを回すためのジョブで、開催日の朝に `install.sh` を
叩く運用が要る。監視プロセスの生存期間とは無関係で、install 忘れがあれば監視は無防備になる。

#### 決定

**監視ループの時間軸を単調タイマーから wall-clock へ移し、「寝ても壊れない」形にする。**
実装は共有骨格 `src/interface/monitor-loop/` に置き、predict-watch / odds-collect の双方を同時に直す。

1. **待機を wall-clock 期限に対する刻み待ちにする**。次スイープの期限（`Local::now() + interval`）を
   決め、刻み幅ごとに現在時刻と期限を比べ直す。復帰時点で期限を過ぎていればループを抜ける
   ＝ **即座に次スイープが走る**（自動再開）。刻み幅は **5 秒**。`tokio::time::sleep` は単調時計基準で
   スリープ中に進まない＝ティックは「起きている時間」でしか消化されないため、8/1 の Standby
   （7 秒 DarkWake が 4 回・累計 28 秒）では 30 秒刻みだと 1 ティックも満了せず再スイープに到達しない。
   5 秒なら DarkWake 1 回ごとに満了して期限超過を検知できる。空回りは既定間隔で 60〜180 回/スイープ、
   1 回あたり時刻比較のみなので無視できる。
2. **途切れを検知して必ず警告する**。**スイープ開始どうしの実間隔（壁時計）**が
   `想定間隔 × 2 ＋ 前サイクルの所要時間` を超えていたら `⚠ 前回スイープから N 分空きました…` を出す。
   待機区間ではなくサイクル間隔で測るのは、スイープ実行中に寝られたケースを取りこぼさないため。
   閾値に所要を足すのは、サイクル自体が長い日（predict-watch は scrape_delay × 対象レース）に
   毎サイクル誤警告が出て警告が無視されるのを避けるため。
   **所要は単調時計（`std::time::Instant`）で測る**——ここを壁時計で測ると
   `実間隔 = 所要 + 待機`・`閾値 = 2×interval + 所要` となって所要が代数的に相殺され、
   発火条件が `待機 > 2×interval` に退化する（＝スイープ中のスリープを検知できない元の欠陥に戻る）。
   単調時計はホストのスリープ中に進まないので、スリープぶんは実間隔にだけ現れ閾値には吸われない。
   **この警告は継続時だけでなく終了時にも通す**。日付を跨いで復帰したケースは 3 の終了経路に入るので、
   そこで黙ると「丸一日未監視だった日」が警告なしの正常終了に見える（＝潰したい静かな失敗そのもの）。
3. **wall-clock の日付で終了する**。`should_stop_by_date(対象日, 現在日)` を **ループ先頭**で評価し、
   対象日を過ぎたら時刻軸の判定に関わらず終了する。先頭に置くのは (a) 前日レースを再スクレイプして
   オッズ時系列を汚す 1 巡を作らないため、(b) `load_slots` が失敗し続ける経路（握って `continue`）でも
   必ず判定を通すため。現在日は**ホストのローカル日付**をそのまま使う（運用ホストは JST 固定で、
   前提が崩れていれば既存の `warn_if_not_today_jst` が起動時に警告する。判定側に TZ 変換を持ち込むと
   コードとテストの基準が割れるだけで、実在しないホストのために複雑さが増える）。
   `--once` は「明示的に 1 スイープだけ回す」指定なので日付では止めないが、過去日なら警告する。
4. **スリープ抑止そのものは骨格の責務にしない**。抑止は既存の launchd エージェント
   `com.paddock.keep-awake`（#264）に一本化し、監視ループは「寝ても壊れない」ことだけに責任を持つ。

#### 理由

- **wall-clock が唯一の正**。監視の目的は「発走時刻までに評価すること」であり、判断の基準は
  常に壁時計。単調タイマーはホストの電源状態という制御外の要因に左右されるので、
  時間軸を壁時計へ揃えるのが構造的な解になる。刻み待ちにすれば、OS がタイマーをどう扱ったかに
  関わらず「今が期限を過ぎているか」だけで正しく判断できる。
- **日付判定は必須で、代替が無い**。`classify` を日付付き（`NaiveDateTime`）に変えて根本から直す案も
  あるが、post_time は DB 上 `TEXT 'HH:MM'` で日付を持たず、当日運用では時刻比較で十分機能している
  （#459 で共通化した不変条件をそのまま活かせる）。**終了判定にだけ日付を足す**のが最小の変更で、
  既存の `classify` / `should_continue` のシグネチャと全テストを無傷に保てる。
- **抑止を骨格に持ち込まない**。8/1 の起点は 13:23 の `Clamshell Sleep`（蓋閉じ）で、`caffeinate -i` の
  守備範囲外＝**抑止を自前で持っても 8/1 は防げなかった**。効くのは 1〜3（寝ても壊れないループ）の側で、
  抑止は best-effort に過ぎない。すでに #264 が同じことをしている以上、骨格に第二実装を置くのは
  ADR 0064 が戒める second source にあたる。責務を分ける方が単純で、壊れる箇所も減る。
- **日付判定に TZ 変換を持ち込まない**。`post_time` が JST 起算なので判定を JST 基準にする案も採ったが、
  運用ホストは JST 固定で非 JST ホストは存在せず、**コードとテストの時刻基準が割れて CI を落とす**
  副作用だけが残った（実際に本 PR のレビュー中に毎日 9 時間 red になる状態を作った）。前提の点検は
  既存の `warn_if_not_today_jst` に任せ、判定はローカル日付のままにする。
- **骨格に入れることで両 app が同時に直る**。#459 で共通化した投資がここで効く。

#### 却下した代替案

- **監視プロセス自身で `caffeinate -i -w <自分の pid>` を確保する**。install 忘れがあっても抑止が効く
  という利点はあるが、(a) 8/1 の実事象（蓋閉じ）は防げない、(b) #264 と機能が重複する、
  (c) 導入すると関数注入の seam・遅延確保・`try_wait` の生存監視・macOS 専用 CI ジョブ・専用テストが
  芋づるで必要になる、の 3 点で割に合わない。抑止は #264 に一本化し、起動手順（keiba-start Step 1.6）で
  install を担保する。issue #568 の要件も「内部で確保する、**あるいは起動手順に組み込む**」と
  後者を許容している。
- **日付判定を JST 固定にする**（`jst_date`）。上記「理由」のとおり、実在しないホストのために
  コードとテストの基準を割る。前提の点検は `warn_if_not_today_jst` に任せる。

- **`classify` を日付付きに変える**。発走状態判定そのものを `NaiveDateTime` 化すれば日付跨ぎは
  原理的に起きないが、post_time が `TEXT 'HH:MM'` である以上どこかで「当日の日付」を合成する必要があり、
  責務が判定関数へ漏れる。既存の単体テスト群（windowed / windowless の境界）も総取り替えになる。
  終了判定にだけ日付を足せば同じ実害が消えるので、変更量に見合わない。
- **launchd の `StartCalendarInterval` で監視を定期起動する（常駐をやめる）**。スリープ中は launchd も
  発火せず（`deployments/launchd/README.md` の既知の限界）、同じ問題が残る。加えて毎回の起動コストと
  スイープ状態の分断が増える。
- **`pmset` の wake スケジュールを持たせる**。sudo が要り、ホストの電源設定を書き換える副作用が
  ユーザの他の用途に及ぶ。監視のために OS 設定を触るのは影響範囲が広すぎる。
- **常時稼働ホスト（RasPi / VM）へ監視を移設する**。これが完全解だが構成変更が大きく、本 issue の
  スコープを超える。`deployments/launchd/README.md` に既存の課題として残っており、本決定はそれと排他ではない
  （移設しても wall-clock 基準の耐性は無駄にならない）。

#### 影響

- **追加**: いずれも crate 内部（`pub(crate)` 以下）。`detect_sweep_gap`（途切れ判定・純関数）/
  `should_stop_by_date`（日付終了判定・純関数）/ `capped_wait`・`minutes_or_max`・
  `effective_interval_minutes`（chrono の範囲外 panic 回避と丸めの単一ソース）。
  `driver` 内に `sleep_until_with_tick` / `next_deadline` / `wait_until_next_sweep` /
  `sweep_gap_notice` / `date_stop_lines`。predict-watch / odds-collect が使う公開 API は
  従来どおり `Sweeper` と `run_monitor_loop` だけ。
- **不変**: `classify` / `should_continue` / `count_started_before_post` / `Sweeper` トレイトの
  シグネチャは変えない。predict-watch / odds-collect 側のコード変更は無い（骨格の差し替えのみで効く）。
- **新しい終了経路**: 対象日を過ぎると
  `── {監視|収集}終了: 対象日（YYYY-MM-DD）を過ぎました。…` を出して終了する。
  過去日を `--date` に渡すと（`--once` 以外は）**1 スイープも走らずに終了する**。
  対象日を回っていたのにスイープ 0 回だった場合だけ、その旨を警告する（起動時点で過去日だった
  ケース＝打ち間違いには出さない。誤用は `warn_if_not_today_jst` が伝える）。
- **`classify` に渡す時刻の取得点が変わった**。従来は `load_slots` 完了後、現在はサイクル開始時
  （`load_slots` 前）。日付判定と発走状態判定で同一時刻を使うための意図的な変更で、差は DB クエリ所要
  （ms オーダー）ぶん。窓 40 分・間隔 5 分のスケールでは実害はない。
- **トレードオフ**: 時間軸を wall-clock に移したことで、NTP のステップ補正や手動の時刻/TZ 変更に
  感度を持つ。前進すれば偽の途切れ警告、**後退すれば待機が延びるうえ実間隔も縮むため沈黙も警告
  されない**（この方向では「必ず警告する」が成立しない）。ホストのスリープで監視が丸ごと死ぬ方が
  実害が大きいので受け入れる。
- **トレードオフ（刻み幅）**: 5 秒ポーリングは awake 中に 1 日最大 17,280 回のタイマー起床になる。
  1 回あたりは時刻比較のみで実害は小さいが、バッテリ運用では皆無ではない。「DarkWake 1 回（7 秒）で
  1 ティック満了する」という 5 秒化の前提自体は**実機の Standby では未検証**（実機検証は
  `pmset sleepnow` からの本格復帰であって DarkWake の再現ではない）。次の開催日の実運用ログで確認する。
- **`--once` はこの保護の対象外**。日付判定で止めないため、過去日を渡した `--once` は警告のうえ
  1 スイープ走り、発走済みレースのオッズを再取得して保存する。cron の日付跨ぎ発火では起こりうる。
- **未来日（前夜仕込み）の盲点は残る**。`should_stop_by_date` は過去日しか止めない。前夜に翌日日付で
  起動すると `classify` が全レースを `Started` と見なし（`now > post`）、`should_continue` が false で
  即「発走前のレースが残っていません」になる。時刻軸だけで判定することの逆向きの同根問題だが、
  本 issue のスコープ外（別途 issue 化する）。
- **スリープ抑止は #264 のまま**。監視バイナリは抑止を持たないので、開催日は
  `deployments/launchd/install.sh`（keiba-start Step 1.6）で keep-awake を有効にする運用が引き続き要る。
  蓋を閉じればどちらにせよ寝る。
- **検証**: 実機の `pmset sleepnow` を跨ぐ手動テスト
  `cargo test -p monitor-loop -- --ignored --nocapture crosses_real_host_sleep` を同梱した
  （DB / netkeiba 非依存。CI では `--ignored` でスキップされるがコンパイルは通るので腐らない）。

### #584: ゲート通過は macOS 通知（osascript）で届け、既存 shell 経路に合流する (2026-08-23) — 採用

#### コンテキスト

`paddock-predict-watch` はゲート判定を stdout に出すだけで、**人に届ける経路を持たない**。
ADR 0072 でスリープ耐性を得た結果、監視は「動いているのに届かない」状態になった。

実測（[docs/original-docs/584-predict-watch-notification.md](../original-docs/584-predict-watch-notification.md)）:
2026-08-09 は 09:43〜18:33 に **82 スイープを途切れ警告 0 件で完走**しながら、判定行は
20,744 行中 192 行（0.93%）に埋もれ、人間は開催終了後にログを掘って初めて内容を知った。
4 開催日 246 スイープでゲート通過（🔶）は 0 件。監視は decision-support（ADR 0055 / 0060）であり、
**人間に届いて初めて機能する**——届かない判定はゼロと同じ。

`deployments/launchd/` には既に通知を伴うジョブがある（`snapshot-coverage`・#493）。監視の主目的である
「買い妙味が出た瞬間」にだけ通知が無いのは非対称だった。

コード上の制約: `evaluate_race` に渡る `SweepCtx` は `Copy` で、`Sweeper::sweep` の戻りは
`impl Future<Output=()> + Send`。**`&mut self` を持てるのは `WatchSweeper::sweep` だけ**だった。

#### 決定

**ゲート通過を macOS 通知で発火させる。配送は既存 shell の `notify()` と同一機構（osascript の
`display notification`）に合流させ、通知手段を増やさない。**

1. **発火閾値は専用フラグ `--notify-roi`（既定 = `--roi-gate`）**。既存 `--notify-gate` は
   🔍 の**表示**閾値のままで、ベルは鳴らさない。`--roi-gate` との大小は制約せず、NaN/∞/負のみ弾く。
2. **`--no-notify` で無効化。既定は有効**（`--once` / cron を含む）。
3. **通知本文は「レース名 / 発走時刻 / 参考ROI / 軸」**。競走名は既存 `race_names_by_date` を
   `load_slots` の 3 本目の日付一括クエリとして引く（N+1 にしない）。ラベルはログ行と同一文字列。
4. **重複抑制は「レースごと初回 ＋ 前回通知時から +10pt 上振れ」**。状態はプロセス内メモリのみ。
5. **判定・本文・注記・ログ行はすべて純関数**（`src/apps/predict-watch/src/notify.rs`）、副作用は
   `send` 1 本。評価関数は通知の材料を**返し**、発火は `&mut self` を持つ `WatchSweeper::sweep` に集約する。
6. **起動時に発火閾値と表示ゲート 2 つを 1 行に並べて宣言する**。ADR 0076 の「通過 0 件」を引くのは
   **実際に測った閾値（≥100%）以上のとき**だけで、`--roi-gate` を下げた探索運用では引かない。
   発火閾値が表示ゲートを下回るとき（`・` 表示のまま鳴る）は起動時に警告する。
7. **配送は 5 秒デッドラインで打ち切り、超えたら子プロセスを kill する**（`spawn_blocking` の中で
   `Child::try_wait()` をポーリング。依存追加なし）。osascript は**絶対パス** `/usr/bin/osascript` で叩く。
8. **配送失敗は連続する間だけ黙り、成功したら再アームする**。`🔔` 行には配送可否を載せる
   （失敗時は `🔔(未配送)`）。

#### 理由

- **経路と閾値は独立に解く**。閾値の妥当性は #571 の担当。経路が無いまま閾値だけ較正すると、
  較正した瞬間の判定がまたログに埋もれる（＝本 issue の再発）。
- **osascript に合流させる実利は権限**。通知許可は #493 で既に付与済みで、`notify-rust` 等を
  入れると別 bundle の許可が要り、**未許可のまま無言で鳴らない**——潰したい沈黙を新しい形で作る。
  ADR 0064 が戒める second source は「同じ判断の二重実装」であって、同じ配送機構を別言語から
  使うことではない。
- **`--notify-gate` を流用しない**。表示帯（#345）と発火の意味が潰れ、「表示を増やしたつもりが
  鳴り出す」「鳴らすつもりで表示だけ増える」の両方向の誤用を生む。名前が紛らわしいぶんは
  help 冒頭のラベル・起動注記・README・用語集の 4 箇所で対比させる。
- **抑制の閾値 +10pt は実測から**。2026-08-09 の新潟10R は 7 スイープ連続で通過帯に入り
  ROI 73.9 → 80.3 → … → 76.1（振れ幅 6.4pt）。このルールなら 7 通知が 1 通知になり、
  かつ「妙味が実際に伸びた」ケースは拾える。
- **失敗するなら鳴りすぎる側へ倒す**。#584 の障害は「届かない」ことなので、抑制の永続化も
  cron での自動無効化も採らない（どちらも沈黙を増やす方向）。

#### 却下した代替案

- **`notify-rust` 等のクレートを入れる**。通知許可の再取得が要り、未許可のまま無言で鳴らない
  ＝ #584 を新しい形で再生産する。ワークスペース全体に依存が増える割に得るものが無い。
- **`--notify-gate` を発火閾値として流用する**。上記のとおり #345 の 🔍 帯が壊れる。
- **`SweepCtx` に `&RefCell<HashMap>` を持たせる**。`&RefCell` は `Copy` なので型は通るが
  `RefCell` は `Sync` でなく、`Sweeper::sweep` の `Send` 制約を満たせない（**コンパイル不能**）。
- **`evaluate_race` の中で直接発火する**。170 行の async 関数に osascript の副作用が埋まり
  テスト不能になるうえ、1 スイープ内の順序・件数を制御できない。
- **同期の `Command::status()` をそのまま async から呼ぶ**（当初案）。既存 shell の `|| true` と
  同じ露出だと考えたが、**shell は単発 cron で常駐ループを持たない**——予想 watch では
  osascript のハングが監視ごと止め、しかも規律 2 の警告も出ない。デッドライン付きで逃がす。
- **配送失敗の報告をプロセス生存期間の one-shot にする**（当初案）。`overrides_checked`（起動時
  1 回の設定ミス検査）と同型に見えたが、配送失敗は**繰り返し起こりうる性質**が違う。一過性の
  失敗 1 回でその日いっぱい沈黙するのは、潰したい静かな失敗を配送側に作ることになる。
- **`tokio::time::timeout` で `spawn_blocking` を包んでデッドラインにする**（一度採ったが棄却）。
  **blocking タスクはキャンセルできない**ので、期限が来ても内側の待ちも子プロセスも残る。
  `#[tokio::main]` のランタイム drop は開始済み blocking タスクを join するため、**監視が正常終了
  した後にプロセスが終われなくなる**（keiba-start の二重起動ガードにも波及する）。
  実効的なデッドラインには `Child::try_wait()` のポーリングと `kill()` が要る。
- **1 スイープあたりの通知件数に上限を設ける**。抑制が定常状態を既にカバーし、初回バーストは
  窓 40 分の Due 件数（通常 10 未満）で頭打ちなので、要件外の複雑さになる。
- **抑制状態を DB / ファイルへ永続化する**。監視を再起動すると**本当に必要な初回通知を落とす**
  側に倒れる。抑制は 1 プロセスの連投抑止であって永続契約ではない。
- **`--once` / cron で通知を自動無効にする**。「cron だけ沈黙する」という新しい静かな失敗を作る。
  鳴らしたくない検証では `--no-notify` を明示する。

#### 影響

- **追加**: `src/apps/predict-watch/src/notify.rs`（`RaceEvaluation` / `resolve_notify_roi` /
  `should_notify` / `pick_notifications` / `record_notified` / `notification_message` /
  `delivery_report` / `notify_status_lines` / `send` / `send_with_deadline`）。
  CLI に `--notify-roi` / `--no-notify`。`Slot` に `race_name`。`WatchSweeper` に抑制状態。
  **依存クレートの追加は無い**（`std::process::Command` のみ）。
- **不変**: `mark_for` / `resolve_notify_gate` / 判定行の表示・`live_ev_snapshots` の verdict・
  monitor-loop 骨格。既存テストは無改変で通る（＝表示ゲートの挙動を変えていない担保）。
  odds-collect は対象外（収集専用で人に届けるゲート判定を持たない）。
- **既定では 1 度も鳴らない**。`--notify-roi` 既定 = `--roi-gate` = 1.0 は ADR 0076 が通過 0 件と
  測った閾値。**これは想定内の状態**で、起動注記がそう宣言する。#571 でゲートが較正されたら
  既定を見直す。ADR 0079 の影響欄「#584 に着手するなら何を通知するかから決め直す必要がある」への
  回答が本エントリにあたる。
- **プロセス再起動で抑制がリセットされる**（全レース初回扱い）。keiba-start の「当日分の監視は
  落とさない」運用が実質の緩和策。
- **表示セッション依存**。`nohup` 起動のログインセッション内なら出るが、SSH / daemon 領域からは
  出ない。一次情報はログの `🔔` 行（配送できなければ `🔔(未配送)`）。osascript は絶対パスで
  叩くので、将来 launchd 化しても最小 PATH の解決問題は起きない。
- **配送は 5 秒で打ち切り、超えた子は kill する**。`spawn_blocking` で executor スレッドを塞がず、
  その内側で `Child::try_wait()` をポーリングして期限超過なら `kill()` ＋ `wait()`（依存追加なし。
  `tokio::process` は workspace の features に無いので使わない）。stdin/stdout/stderr を
  全て null にして端末待ちも作らない。**1 件でもデッドラインに掛かったらそのスイープの残りは
  配送を試みない**（1 件 5 秒がレース数ぶん直列に積み上がるのを止める）。
- **配送できないプラットフォーム（macOS 以外）では通知経路ごと落とす**。試しても必ず失敗し
  抑制状態も進まないので、同じレースが毎スイープ `🔔(未配送)` を積み上げる——#584 が減らそうと
  した埋没を通知行側で再生産することになる。起動注記も同じ条件で「配送できません」と宣言する。
- **`load_slots` に日付一括クエリが 1 本増える**（毎スイープ 1 回・N+1 ではない）。
- **検証**: 純関数の単体テストに加え、**2026-08-09 新潟10R の実測 ROI 列を流して 7 通知が 1 通知に
  落ちることを固定**した。起動注記は 4 分岐（既定 / `--roi-gate` 引き下げ / `--notify-roi` 明示 /
  表示ゲート未満）を文言ごとテストで固定し、実バイナリでも確認済み。osascript の実発火は
  `--ignored` の手動テスト `sends_real_notification`（本文に `"` と `\` を混ぜ、argv 渡しの
  検査を兼ねる）。**実際にゲートを通過したレースで通知バナーが出る end-to-end は次の開催日に確認する**
  （実装日 2026-08-23 20:05 時点で当日の全レースが発走済みだった）。
