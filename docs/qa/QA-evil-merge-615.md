# QA — マージコミットに対する stale 判定（#615 (a)）

一次資料: [docs/original-docs/0084-evil-merge-is-visible-to-stale-check.md](../original-docs/0084-evil-merge-is-visible-to-stale-check.md)

親 issue: [#615](https://github.com/taito-station/paddock/issues/615)（転記しない・ADR 0074）。
本文は `gh issue view 615` で取得する。

## Q0: evil merge は本当に不可視なのか（実装前に実測する）

- 観測/根拠: ADR 0081 の「既知の限界 (1)」と `scan_last_content_change` のコメントが揃って
  「マージコミットは `git show` が既定で差分を出さないので evil merge は恒久的に不可視」と
  書いている。まず本リポジトリの履歴で数えた。

  | 実測（main `d46ace4` 時点） | 件数 |
  |---|---|
  | `git log -- <path>` が列挙したマージ × `sources` パス | **7 組** |
  | うち `path_status` が検出（`MM` / `MA` / `AA`） | **7 組** |
  | うち不可視（`status is None`） | **0 組** |

  合成 fixture でも確認した: A 真の evil merge → `MM`・マージ自身を返す /
  B 片親を採るマージ → `None`・祖先に帰属 / C マージ内の純粋リネーム → `RR`・マージ自身
  （偽 STALE）/ D octopus の evil merge（3 親）→ `MMM`・マージ自身。
- 回答: **確定。不可視ではない。** `git show` はマージに対し既定で combined diff（`--cc`）を出し、
  `--cc` は「**全ての親と異なる**パス」を列挙する——evil merge の定義そのもの。片親と同じ内容に
  なったマージは列挙されないが、その内容を作ったコミットが祖先に実在するので飛ばしてよく、
  `git log` の TREESAME 単純化も同じ基準で辿る。**対象集合が一致するので穴が無い。**
- 反映先: ADR 0084 コンテキスト・実測 / `scan_last_content_change` のコメント訂正

## Q1: 「起こりうるか」の答えは何か

- 観測/根拠: issue の要件は「現実に起こりうるかをまず確認し、起こらないなら『検出しない』と
  明記して閉じるのも可」。実測では **evil merge は日常的に発生している**——PR ブランチが main を
  取り込んでコンフリクトを手で解消すると、どちらの親にも無い内容がマージコミットに生まれる。
  `8ec61a18`（#613 の main 取り込み）がその実例で、`docs/qa/QA-sources-coverage-checks-596.md`
  の内容はそのマージにしか存在しない。
- 回答: **確定。起こりうる（し、起きている）。ただし検出できているので実装は足さない。**
  issue が想定した 2 択（塞ぐ / 起こらないので閉じる）のどちらでもなく、
  **前提が誤っていた**という第 3 の結論になった。
- 反映先: ADR 0084 決定 1

## Q2: 実装を足さないなら、何を成果物にするか

- 観測/根拠: `--cc` は `git show` の**既定**であって呼び出し側に明示されていない。
  `--first-parent` を足す・`git diff-tree`（`-c` 無し）へ置き換える、といった変更で黙って失われる。
  実測でも `git diff-tree` への置換で evil merge が見落とされた。
- 回答: **確定。契約テストで固定する。** 実装は変えず、`--cc` を失う退行で落ちるテストを置く。
  誤ったコメント（実装・ADR 0081 の両方）も訂正する——「ここは不可視」と書いてあると、
  次に読む人が塞ぐ必要のない穴を塞ぐか、検査されている経路を「どうせ見えない」と扱う。
  #615 の起票自体がその実例。
- 反映先: ADR 0084 決定 2 / `test_evil_merge_is_detected_as_content_change`

## Q3: その契約テストはどう書けば「効く」のか

- 観測/根拠: **最初に書いたテストは何も識別していなかった。** `path_status` がマージで
  `(None, None)` を返す変異を注入しても緑のままだった。原因は 2 つ:
  (1) ヘルパが `ours` をコミットせずに `git merge` していたので**そもそもマージが作られていなかった**
  （親が 1 つ）、(2) 直しても、マージが不可視になった際に**親側の変更が STALE を出す**ので
  exit 1 が変わらない。
- 回答: **確定。両親の変更を免除対象（ピン更新のみ）で挟む。** 同じピンを両側で別の hex へ
  動かせば必ずコンフリクトし、どちらの親も「内容変更ではない」。マージの解決でステップ名を
  変えれば、**マージだけが内容変更**になる。これでマージが不可視になった瞬間に緑へ転ぶ。
  対照群 `test_pin_only_merge_is_not_stale`（解決も免除対象のまま）を置いて、exit 1 が
  「マージだから」ではなく「内容が変わったから」であることを分離する。
- 反映先: ADR 0084 決定 2 / `test_pin_only_merge_is_not_stale`

## Q4: マージ内リネームの偽 STALE は塞ぐか

- 観測/根拠: 実測 C のとおり、combined diff はリネームを `RR` として出す（`R100` ではない）。
  `scan_last_content_change` の免除は `status == "R100"` を見るので当たらず、`-M100%` も
  マージには効かず、リネーム元も取れない。結果、**マージ内での純粋なリネームは偽の STALE** になる。
- 回答: **確定。塞がず記録する。** fail-closed 側で、偽の STALE は sha 追従で解消できる
  （見落としと違って気づける）。発火実績も無い。塞ぐには各親に対して `-M100%` 付きの diff を
  取り直す実装が要り、`path_status` の戻り値の形も変わる。**現状の挙動として** pin し、
  将来直すならそのテストを反転させるのが入口になる。
- 反映先: ADR 0084 決定 3 / `test_rename_inside_merge_is_treated_as_content_change`

## Q4b: 「対象集合が一致するので穴が無い」は本当か（2 巡目の自己検証）

- 観測/根拠: この主張は議論であって計測ではなかった。**変異マトリクス**（11 変異 × 183 ケース）を
  回したところ、`status is None` の分岐を「内容変更」に変える変異が**どのテストでも落ちなかった**。
  そこで当該分岐に計装を入れて到達回数を数えたら、**実リポジトリ全体（`sources` 110 パス・
  全履歴）でも 183 ケースでも 0 回**だった。
  なお当初は「clean auto-merge（両側の変更を機械的に統合したマージ）が `--cc` の
  hunk 圧縮で落ちるのでは」と仮説を立てたが、実測では `MM` で列挙され**外れ**だった。
- 回答: **この回答は 2 巡目のレビューで覆った。下の Q4c が正。**
- 反映先: —（Q4c を見る）

## Q4c: Q4b の計測と結論はどちらも誤りだった（2 巡目レビューでの訂正）

- 観測/根拠: 2 名のレビュアーが独立に再現し、こちらでも確かめた。
  1. **計測が壊れていた。** テストは checker を `subprocess.run(..., capture_output=True)` で
     起動するので、**stderr へ出す計装はサブプロセス内で捕捉されて外に出てこない**。
     ファイルへ追記する計装（環境変数でパスを渡す）に変えると、183 ケースでの到達は
     **0 回ではなく 1 回**だった（`test_noncanonical_source_is_error` の非正規形パス）。
  2. **機構の説明も誤り。** この分岐に来る原因は `git log` と `--cc` の集合差ではなく、
     `path_status` が name-status の**終点一致**（`parts[-1] == path`）しか見ないこと。
     **非マージのコミットで起きる**——合成履歴で再現: `c1` が `P.md` を作り `c2` が
     `P.md` → `Q.md` の純粋リネーム。`git log -- P.md` は `c2` を列挙するが
     `path_status(c2, "P.md")` は終点が `Q.md` なので `(None, None)`（`c2` は親 1 つ）。
  3. **結論が逆だった。** 「防御的で通らない」ではなく、**`continue` は load-bearing**。
     `return sha` に変えると純粋リネーム地点を内容変更と誤認して**偽の STALE** を出す。
- 回答: **確定。** 実測は実リポジトリ 0 回 / 回帰テスト 1 回。分岐はマージとは無関係で、
  終点一致の帰結。当初**どのテストもこの分岐を pin していなかった**（`return sha` 変異で 183 ケースが
  全通過した）ので、`test_rename_source_commit_is_skipped_not_attributed` を足した。
  両側と解決を免除対象（frontmatter のみ）にして走査がリネーム地点まで届く履歴を組み、
  side を第 1 親にする必要がある（base を第 1 親にすると `is_metadata_only_change` が
  比較対象を取れず免除が効かない）。
- 反映先: ADR 0084 実測 4 / `scan_last_content_change` のコメント / `ci-pipeline.md`

## Q5: ADR 0081 の誤りをどう扱うか

- 観測/根拠: CLAUDE.md は「一度置いた ADR は改変しない——決定を変えるときは新しい ADR で
  supersede する」と定めている。0081 の**決定**（例外 1d・`ScanAborted` の error 昇格）は
  正しく、誤っていたのは「影響」節に書かれた**限界の記述**だけ。
- 回答: **確定。0081 の本文は触らず、新しい ADR 0084 で訂正する。** 決定を覆すわけではないので
  supersede ではなく「訂正」と位置づける。0081 の「既知の限界 (2)」（CRLF）は有効なまま。
  knowledge 側（`ci-pipeline.md`）の写しは 0084 に従って書き換える——**読む入口は knowledge** なので、
  そちらが古いままだと訂正が届かない。
- 反映先: ADR 0084 決定 4 / `docs/knowledge/ci-pipeline.md`
