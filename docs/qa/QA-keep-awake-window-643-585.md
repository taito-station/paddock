# QA: keep-awake の抑止窓の追従（#585）と lock パス（#643）

対象: `scripts/predict-check/keep_awake.sh` / `deployments/launchd/uninstall.sh` の設計判断。
実測は [585-keep-awake-window-gap.md](../original-docs/585-keep-awake-window-gap.md)、
運用上の限界の記述は `deployments/launchd/README.md` が正。

---

## Q1. lock は `${TMPDIR}` 配下と UID スコープの固定パスのどちらにするか

#643 が「**実装前にどちらが同じパスに解決されるか実測する**」と要求していた点。

**実測（2026-08-19）**: 端末の `TMPDIR` は `/var/folders/wq/.../T/`、**launchd は `TMPDIR` 未設定**で
`${TMPDIR:-/tmp}` が `/tmp` に落ちる。`id -u` は両経路とも 501。

**回答: UID スコープの固定パス `/tmp/paddock-keep-awake-$(id -u).lock.d`。**

`${TMPDIR}` を使うと launchd と端末が別 lock を見て互いを見失い、**uninstall が caffeinate を
止められない / keep-awake が二重起動する**という、直そうとしている問題より悪い状態になる。
リポジトリの既存判断（`prefetch_odds.sh`「ロックパスは WORKDIR に依存させず固定にする」）とも一致。

**ただし #643 の懸念が「解消する」わけではない**（レビューで訂正）。`/tmp` は world-writable で、
sticky bit が禁じるのは**他人のエントリの削除・改名だけ**であり、新しい名前の作成は誰でもできる。
他ユーザーが `/tmp/paddock-keep-awake-<uid>.lock.d` を先回りして作れば `mkdir` も `rm` も失敗し続け、
keep-awake は**無言で停止**する（#264 が最も避けたい状態）。uid を挟んで消えるのは
**同一ホストの別ユーザーとの事故衝突**であって、悪意ある先回りではない。

そこで lock 取得に失敗したとき所有者を見て分岐し、自分の所有でなければ**大きく警告する**
（「lock 競合で取得失敗」と同じ 1 行で流すと気づけない）。恒久対処として `$HOME` 配下
（`~/Library/Caches/...`）へ移す案はあるが、`prefetch_odds.sh` の lock（#651）と揃えて別途扱う
——本 PR で片方だけ移すと、既存の「lock は /tmp の固定パス」という流儀が中途半端に割れる。

反映先: `keep_awake.sh` / `uninstall.sh` の `LOCK_DIR`、`deployments/launchd/README.md`。
担保: `test-keep-awake.sh` の「作成側と削除側が同一の uid スコープ lock パス式を持つ」。

## Q2. lock パスの二重定義（作成側 / 削除側）をどう扱うか

`LOCK_DIR` は `keep_awake.sh` と `uninstall.sh` の両方が持つ。ADR 0064 が戒める second source の形。

**回答: 二重定義は残し、機械検査で一致を担保する。**

共有 shell ライブラリはこのリポジトリに存在せず、`LOCK_DIR` 1 つのために新設するのは過剰
（`prefetch_odds.sh` も同じ流儀で固定文字列を持っている）。代わりに
**両ファイルが同一の式を持つことをテストで検査**し、片方だけ変えたら落ちるようにした。
両ファイルに「相方も同時に直すこと」のコメントも置く。

反映先: `test-keep-awake.sh` のケース 8。

## Q3. 稼働中 caffeinate の残り時間をどう知るか

**回答: lock に終了時刻（絶対エポック秒）を `end` として記録する。**

**理由**: 残り時間を外部から観測する手段がリポジトリに無い（`ps -o etime` の解析も `pmset` からの
残り時間取得も前例ゼロ。そもそも `pmset -g assertions` は残り時間を持たない）。観測できない以上
記録するしかなく、**既存の `pid` ファイル方式と同型**にするのが素直。

`pid` の**後**に `end` を書く。途中で死ぬと「pid はあるが end が無い」中間状態になるが、これは
「end 不明 → 安全側に倒して張り直す」に落ちるので害がない（逆順だと end だけ新しく残って
古い窓を信じてしまう）。

担保: `test-keep-awake.sh`「延長後の lock に新しい pid と end が記録される」「end 未記入の lock は
安全側に倒して張り直す」。

## Q4. 張り直しの順序（新を起動してから旧を落とす / 逆）

**回答: 新を起動してから旧を落とす。** issue #585 の要件「張り直し時は抑止の空白を作らない順序」。

逆順（kill → start）にすると kill から起動までの窓で抑止がゼロになり、**いま直そうとしている
「最大 5 分の空白」を小さく再現する**。一瞬 caffeinate が 2 本重なるが、どちらも `-t` で自動終了
するので無害。旧を落とせなかった場合も、二重に抑止が掛かるだけで実害は無い（warn を出す）。

担保: `test-keep-awake.sh`「起動→停止の順序（抑止の空白を作らない）」。
**変異検査で確認済み**——順序を反転させるとこのテストだけが落ちる。

## Q5. 判断できないとき（`end` が読めない・壊れている）はどちらに倒すか

**回答: 延長が必要とみなして張り直す。**

抑止を切らさない側＝安全側。旧形式の lock（`pid` のみ）からの移行もこの経路で自然に吸収される。
#632 で採った「迷ったら取り直す」と同じ向き。

## Q6. 旧 lock パスの移行をどう扱うか

**回答: 新パスで lock を取る前に、旧 `/tmp/paddock-keep-awake.lock.d` を 1 回だけ見て回収する。**

これが無いと、修正前の launchd が起動した caffeinate が残ったまま新コードへ切り替わったとき、
新コードは旧 lock を見ないので**二重起動**する（片方は誰も止められない）。生きていれば pid を
引き継いで張り直し、死んでいれば旧ディレクトリを掃除する。移行後は旧パスが二度と作られない。

担保: `test-keep-awake.sh` ケース 7（ただし旧パスが実在する環境では**実運用の caffeinate を
横取りしないよう skip する**）。

## Q7. ADR を起票するか

**回答: 起票しない。**

**理由**: 「lock の置き場所」「抑止窓の決め方」を決定として固定した ADR は存在しない
（`keep_awake.sh` のハードコードと README の記述だけ）。ADR 0072 決定 4 は
「スリープ抑止は監視バイナリの責務にせず #264 に一本化」という**責務境界**だけを固定しており、
`keep_awake.sh` 内部の改善はそれと整合する（むしろ「抑止は #264 が担う」という前提を強化する）。
supersede も新 ADR も不要。

**ADR が要るのは次のいずれかを採るとき**（今回は採らない）:
- 抑止を監視バイナリ側に持たせる → ADR 0072 決定 4 の supersede
- `pmset` の wake スケジュールを使う → ADR 0072 の却下案の再評価
- **END の定義そのものを変える** → `snapshot_coverage_check.sh`（#493）が同じ END 基準を共有しており、
  発火タイミングに波及する

本 PR は **END の定義を変えず**、計算済みの END に caffeinate を追従させるだけなので波及しない。

## Q9. テストで実 `caffeinate` を起動するか

**回答: 起動しない。PATH 差し替えのスタブを使う。**

実 `caffeinate` を起動するとテストが実機のスリープ抑止に触る。スタブは
`psql`（最終 post_time を返す）/ `caffeinate`（引数を記録して `sleep` に化ける）/
`ps`（`-p PID -o comm=` に `caffeinate` を返す）の 3 つ。

`ps` までスタブするのは、スタブ caffeinate が shebang スクリプトのため**実 `ps` では `comm` が
`bash` になり稼働中判定が成立しない**から。`kill -0` / `kill` は実 pid に対する本物を使う。

**実装中に踏んだ罠**: 偽 caffeinate を `sleep 300 &` で起こす関数を `$( )` の中で呼ぶと、背景
プロセスが置換の stdout パイプを握ってテストが 300 秒固まる。`>/dev/null 2>&1` で fd を落とす。
また **起動有無をスタブのログ行数で判定すると競合する**（`nohup` された背景プロセスの書き込みが
親の終了に間に合わない）ので、`keep_awake.sh` 自身が同期出力する起動ログで判定する。

**旧 lock パスも env で注入する**（`PADDOCK_KEEP_AWAKE_LEGACY_LOCK_DIR`）。移行処理は全ケースで
無条件に走るので、注入できないと**テストが実運用の旧 lock を読んで本物の caffeinate を kill する**。
「旧パスが実在したら skip」で逃げるのは不可——一度でも旧パスが残ると以後永久に skip が続き、
移行ロジックの回帰が無検査になる（偽陰性）。同じ理由で**期待ケース数を assert する**
（`FAIL=0` だけ見ると、ケースが丸ごと飛ばされたときに「全部通った」と読めてしまう）。

## Q10. 抑止終了時刻を分境界へ丸めるか（レビューで発見した欠陥）

素朴に書くと `END_EPOCH = $(date +%s) + SECS` になるが、**これは壊れている**。

`SECS = (END_MIN - NOW_MIN) * 60` は分粒度（`NOW_MIN` は秒を切り捨てている）なので、展開すると

```
END_EPOCH = (その日の0時 + NOW_MIN*60 + 秒針 s) + (END_MIN - NOW_MIN)*60
          = 真の終了時刻 + s
```

つまり **lock に実行時刻の秒針が乗る**。次サイクルの比較 `cur_end >= END_EPOCH` は
「前回の秒針 >= 今回の秒針」に退化し、`StartInterval` の刻みで秒針は毎回変わるので、
**post_time が全く変わらなくても約半数のサイクルで「延長する」と誤判定して健全な caffeinate を
kill→再起動する**。抑止は切れない（新を起動してから旧を落とすため）が、
**この PR の中核である「延長要否の判定」がログ上も挙動上も無意味になる**。

**回答: エポックを 60 で丸める**（`$(date +%s) / 60 * 60 + SECS`）。JST のオフセットは分単位なので、
丸めた値は TZ に依らず「現在の分の開始」に一致する。これで post_time が同じ限り END_EPOCH は
毎サイクル同値になり、比較が決定的になる。

**テストがこれを見逃した理由**も記録しておく。当初の据え置き / 延長ケースは `end` を
`now+86400` と `now+60` という両極端に置いており、**分未満の誤差を踏む余地が無かった**。
さらに回帰テストを足した後も、**2 回の実行が同一秒内に収まると `date +%s` が同値になり
欠陥版でも通ってしまった**（変異検査で発覚）。実運用の launchd は 300 秒間隔で秒針が必ず変わるので、
テスト側も 2 回目の前に `sleep 1` を挟んで**その条件を再現する**。

## Q11. 旧 lock ディレクトリをいつ消すか

**回答: 引き継いだ pid を確実に停止し切った後だけ消す。** 読んだ直後には消さない。

読んだ直後に消すと、その先の early exit（延長不要 / 別プロセス起動中 / lock 競合）を通ったときに
**生きた caffeinate の pid 記録だけが失われる**。以後どの実行からも `uninstall.sh` からも止められない
孤児になり、最終 post_time まで抑止が居座る——#264 が最も避けたい状態を、移行処理で自ら作ることになる。

同じ理由で「置き換える対象の pid」は**単一変数でなく配列**にする。現行 lock 側と旧パス側の両方が
生きている移行期に、単一変数だと後から代入した方で上書きされ、もう片方が孤児になる。

据え置き（現行 caffeinate が窓を満たす）経路でも、引き継いだ旧 pid は停止して旧ディレクトリを消す。
現行が既に窓を握っているので、ここで落としても抑止の空白は生まれない。

## Q12. 旧 lock の回収を `uninstall.sh` にも入れるか

**回答: 入れる。** 作成側だけに入れると移行が非対称になる。

新コードの tick が 1 度も走らないうちに夜の `uninstall.sh` を叩くと、新パスに pid が無いので
**旧 caffeinate を止められない**。これは Q1 で `$TMPDIR` を却下した理由（「uninstall が caffeinate を
止められない」）とまったく同じ壊れ方で、それを移行経路で自ら作ることになる。

`uninstall.sh` の `trap` 構造（PR #641 が 3 巡かけて到達した「削除してよいと確定したときだけ
フラグを立てる」形）は壊さず、旧パス用のフラグを足して同じ trap で消す。

旧パスは symlink / 他ユーザー所有なら触らない——`pid` ファイルの中身がそのまま `kill` の引数に
なるため、書き換え可能なディレクトリを信用してはいけない。

## Q13. lock の信用検査をどこに置くか

**回答: 中身（`pid` / `end`）を読む前。** mkdir 失敗時だけ所有者を見る作りでは足りない。

先回り者が「生きた caffeinate 相当の pid ＋ 遠い未来の end」を仕込むと、稼働中→据え置き経路に
入って `exit 0` し、ログには「延長不要・据え置き」という**無害な行しか出ない**。抑止はゼロなのに
正常に見えるので、README が謳う「警告が無ければ抑止は効いていた」という運用契約が崩れる。

検査は `[ ! -L ] && [ -d ] && [ -O ]` の順で行う。**`-L` を先に見るのが要点**——`-d` と `-O` は
symlink を辿るので、自分が所有するディレクトリを指す symlink を置かれると所有者検査だけでは
素通りする（`/tmp` の sticky bit は他人のエントリの削除を禁じるだけで、symlink の作成は防げない）。

`pid` は数値でなければ「記録なし」に倒す。`kill` に `-1` を渡すと
**signal を送れる全プロセスが対象**になるため、先回りで仕込まれた値をそのまま渡してはいけない。

## Q14. `uninstall.sh` を叩くテストで `HOME` をどう扱うか

**回答: 必ずテスト用サンドボックスへ差し替える。**

`uninstall.sh` は `$HOME/Library/LaunchAgents/com.paddock.*.plist` を `launchctl unload` して
`rm -f` する。素で叩くと**実機の稼働中エージェント 3 本（prefetch-odds / keep-awake /
snapshot-coverage）が消える**。CI（ubuntu）は plist が存在しないので常に緑になり、
**この危険は CI では一切可視化されない**——だからテスト側で明示的に固定する。

`launchctl` もスタブする（二重防御）。差し替えが効いていること自体も
「未インストール: <TESTROOT>/home/...」の出力でアサートする。

## Q15. どこまで変異検査で担保できたか（担保できていない範囲）

「テストが緑」を「検査した」と読み替えないために、**変異検査で落ちることを確認した範囲**と
**確認できていない範囲**を分けて記録する。

**落ちることを確認した**（変異 → 落ちるテスト）:

| 変異 | 落ちるテスト |
|---|---|
| `END_EPOCH` の分丸めを外す | 「2 回目は据え置き」「end は分境界」 |
| 据え置き経路で旧 lock を無条件削除 | 「据え置き時に落とすのは旧パス側だけ」 |
| 旧 lock の削除を early exit より前に戻す | 「早期 exit で旧 lock を消さない」 |
| 置き換え対象を単一変数の上書きに戻す | 「両方が生きていれば両方停止する」 |
| `comm` の末尾アンカーを外す | 「comm の末尾アンカー」 |
| lock の信用検査を外す | 「lock が symlink なら警告して抜ける」 |
| `end` の数値検証を外す | 「end が非数値の lock は張り直す」 |
| `uninstall.sh` の旧パス fallback を外す | 「uninstall.sh は旧 lock パスも停止する」 |
| 張り直しを kill → start へ反転 | 「起動→停止の順序」 |

**確認できていない**:

- **`pid` の数値検証**——ガードを外した変異でテストが 10 分以上ハングし、原因を特定できないまま
  アボートした。`-1` は「signal を送れる全プロセス」を意味する値なので、原因不明のまま再実行するのは
  危険と判断した。正常系（「別プロセス起動中」になり、ログに `pid=-1` が出ない）は固定してある。
- **`kill` に失敗した場合に旧 lock を残す経路**——`kill` は shell builtin なので PATH スタブで
  差し替えられず、自分が所有するプロセスの kill を失敗させる手段が無い。コードレビューでのみ担保。
- **lock 取得競合（rm と mkdir の隙に別プロセスが割り込む）**——決定的に再現する手段が無い。

**1 巡目のテスト自身にも穴があった**: 追加した回帰テストが 2 回の実行を同一秒内に収めてしまい、
欠陥版でも通っていた（変異検査で発覚）。また変異の置換文字列が実ファイルと 1 文字ズレていて
**変異が適用されないまま「テストが落ちない」と読みかけた**——変異検査は「変異が実際に入ったか」まで
確かめないと、何も検査していないのと区別がつかない。
