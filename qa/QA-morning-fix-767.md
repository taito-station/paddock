# QA: 買い目の固定を朝の選定へ前倒しする（#767・2026-10-05）

#724 で REQ-D01-003 の「事前データで確定」を「朝の時点で固定」と解釈し（`qa/QA-fix-timing-724.md` Q5）、
その前倒しを実装するときに確定した方針の記録。蒸留先: `knowledge/ev-kelly-bet-selection.md`（REQ-D23-007・決定ログ #767）、
`knowledge/product-goals.md`（REQ-D01-003）、`knowledge/glossary.md`（軸ロック）。

## Q1: 朝の選定の作り方

- 選択肢: **朝のスナップショットから機械的に組む**（推奨）/ 朝の predict・overview の結果を記録する。
- 回答: **朝のスナップショットから機械的に組む**。朝の定義は #724 と同じ「当日 JST 0 時以降で最初に保存された単勝」。
  #724 の部品（`predict_race_views_at`・`compose_portfolio`・`PinnedSelection::from_staked_legs`）を使う。
  predict を実行しなくても作れ、ADR 0078 で却下した「人手の記録頼み」を避けられる。

## Q2: 計算の時点と記録先

- 選択肢: **predict-watch が計算し新テーブルへ**（推奨）/ 朝に専用 CLI で一括計算 / `live_ev_snapshots` に朝の行を入れる。
- 回答: **predict-watch が計算し、新テーブル `morning_selections` に保存する**（レースごと 1 行・先勝ち）。
  `live_ev_snapshots` は「最古行＝初回スイープ」を前提に計測（gate_calibration・#724 の再構成）と盤のフリップ判定が読んでいるので使わない。

## Q3: 記録◎ の優先

- 選択肢: **維持（記録◎ → 朝 → T-40 → なし）**（推奨）/ 朝の選定を最優先。
- 回答: **維持**。
- 追加の確認（計画の敵対的レビューを受けて）: 記録◎ と朝の軸が食い違うと、軸だけ差し替えると相手が 4 頭に減り
  モデルの首位が買い目から消える。→ **朝の選定を計算するときに記録◎ を軸に強制して組む**（今の初回スイープと同じ形）。
- 追加の確認（PR のセルフレビューを受けて）: 朝の選定を保存した後に記録◎ が入ると、盤は軸を差し替え predict-watch は
  差し替えず、両者が食い違っていた。選択肢は「朝の後の記録◎ は使わない」（推奨）/「predict-watch も盤にそろえる」/
  「記録◎ が入ったら朝の選定を作り直す」。→ **朝の後の記録◎ は使わない**（盤・predict-watch とも）。

## Q4: 盤（`/races/{id}/board`）

- 選択肢: 今回は出さない（推奨）/ **盤にも出す**。
- 回答: **盤にも出す**。追加の確認で、**盤の買い目も朝の選定で固定する**（記録◎ → 朝 → なし）。
  盤は読むだけで、朝の選定を計算・保存するのは predict-watch だけ。
- 改訂（PR のセルフレビュー・Q3 の追加の確認）: 盤の優先順も **朝の選定 → 記録◎ の軸だけ → なし** に改めた
  （朝の選定を保存した後に入った記録◎ は使わない）。

## 前提として進めた軽微な点

- 切り替えのフラグは作らない（朝の固定を既定にする）。朝の選定が無いレースは初回スイープ（T-40）の固定に戻る。
- 開催日の日中にはマージしない。
