# QA: 確定オッズの遡及取得と着順の補完（#721・2026-09-29）

#721 の計画承認時に確定した方針の記録。一次資料: `docs-original/721-final-odds-backfill.md`。
蒸留先: `knowledge/netkeiba-datasource.md`（決定ログ #721）・`knowledge/race-result-ingestion.md`（過去日の着順取り込みの間隔）。

## Q1: 確定オッズを遡って取る範囲

- 選択肢: **結果のある全レース**（推奨・約 5,000R）/ #720 の確率がある範囲だけ（2025-07〜・約 3,400R）/ まず 1 か月分で試す。
- 回答: **全レース**。あわせて「高速化不可？」と質問があった。
- 回答への答え: 間隔は縮めない（バルク取得は 3 秒以上・1〜2 秒の連打はしないというユーザーの明言があり、開発ルール監査で
  計画初版の 1.2 秒を差し戻した）。高速化の手段はリクエスト数を減らすことだけで、1 回の呼び出しで複数券種が返るかを実測した
  （返らなかった・一次資料 §1）。並列化もしない。

## Q2: 保存先

- 選択肢: **ファイル（生の応答 JSON ＋ 解析用 TSV）**（推奨）/ DB の新テーブル / `race_odds_snapshots` に追記。
- 回答: **ファイル**。`race_odds` は上書きせず、DB に表を作らない。

## Q3: 出馬表だけあって結果の無いレース（457R）

- 選択肢: **取り込む**（推奨）/ 今回は取り込まない。
- 回答: **取り込む**。共有 DB への書き込みは、隔離 DB で検証 → バックアップ → 共有 DB の順で行う（issue の制約）。

## Q4: 実装の置き場所（作業中の判断・開発ルール監査で是正）

- 計画初版は Python で取得・パースする案だったが、ドメインのデータ処理は Rust という区分（ツール層とドメイン層を混同しない）と
  二重実装の回避（ADR 0064）に反するため、Rust（既存の netkeiba-scraper とドメインの番兵判定を再利用）に改めた。
- api-server の netkeiba 取得間隔を設定できなかったので、`PADDOCK_NETKEIBA_INTERVAL_MS` を足した（未設定なら従来どおり）。
  `paddock-fetch-results` に INSERT のモードを足す案は、ADR 0015（UPDATE 専用）の契約を変えるので採らなかった。

## 帰結

- 最古側（2025-01）まで確定オッズを遡って取れる。457R の着順は共有 DB に取り込み済み（隔離 DB と結果が一致）。
- 全レースの確定オッズは `~/paddock-backups/pinned/721-final-odds/` に取得（件数・照合は一次資料）。#722 の入力になる。
